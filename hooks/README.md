# hooks/ — защитные хуки

Рабочая реализация принципа [09 — Механические инварианты](../principles/09-mechanical-invariants.md): то, что нельзя доверить тексту промпта, проверяется кодом.

> **Слой платформы.** Это единственная папка репозитория, привязанная к Claude Code. `principles/`, `templates/` и `checklists/` остаются провайдер-нейтральными. Для других платформ смотри раздел [Другие платформы](#другие-платформы) — механика различается, идея нет.

## Что блокируется

| Правило | Инструмент | Что ловит | Класс |
|---|---|---|---|
| `fs` | Bash | `rm -rf` по корню, `~`, `.`, `..`, маске или пути с переменной | P |
| `git` | Bash | `push --force` и `+рефспек`, `--mirror`, удаление ветки на сервере, `reset --hard`, `clean` без сухого прогона, `checkout -- .` и `restore .` | P / W |
| `sql` | Bash | `DELETE` и `UPDATE` без `WHERE`, `DROP`, `TRUNCATE` | P |
| `env` | Bash, Edit, Write | запись в `.env` и `.env.*` — и редактором, и через оболочку | P |
| `memory` | Bash, Edit, Write | запись роли за пределами её зоны — и редактором, и через оболочку | W |

Отдельно от них — `verify.py` на событии `Stop`: не даёт завершить работу с падающими тестами. Ставится по желанию, см. раздел ниже.

Правило `env` намеренно двустороннее. Проверять только Edit и Write бессмысленно: `echo KEY=... > .env` пишет в файл мимо этих инструментов, и защита, закрывающая одну половину, создаёт лишь видимость. Чтение (`cat`, `grep`, `source`) не ограничено.

Правило `git` смотрит на смысл, а не на написание: `git push origin +main` — тот же force-push, что и `--force`, только другим синтаксисом.

Каждая блокировка объясняет причину и предлагает альтернативы. Хук, который просто говорит «нельзя», учит обходить себя.

> ⚠ **Не ставь двумя способами сразу.** Плагин и ручная копия в `.claude/hooks/` не дополняют друг друга, а дублируют: каждый хук срабатывает дважды. Счётчик правила трёх попыток растёт вдвое быстрее — повтор блокируется после второй попытки вместо четвёртой, — а записи журнала задваиваются. Замерено на живой сборке: одна команда дала две записи, одно падение подняло счётчик на два. `session_start.py` такое сочетание обнаруживает и предупреждает каждую сессию, пока его не уберут.

### Правило memory

Поле `memory` во frontmatter субагента выдаёт ему Read, Write и Edit **в обход списка `tools`** — чтобы он мог вести файлы памяти. Для роли, лишённой Write или Edit намеренно, это снимает главное ограничение. Правило `memory` возвращает ограничение обратно:

| Роль | Разрешено писать |
|---|---|
| `pm-orchestrator` | только своя папка памяти |
| `code-reviewer` | только своя папка памяти |
| `security-reviewer` | только своя папка памяти |
| `investigator` | только своя папка памяти |
| `design-reviewer` | только своя папка памяти |
| `scope-challenger` | только своя папка памяти |
| `finops-engineer` | только своя папка памяти |
| `unit-economics-analyst` | только своя папка памяти |
| `investment-analyst` | только своя папка памяти |
| `vendor-auditor` | только своя папка памяти |
| `browser-tester` | своя папка памяти и E2E-каталог — только через `Write`; `Edit` там тоже заблокирован |
| `devops` | своя папка памяти; `Edit` существующих файлов не ограничен |
| `local-sysops` | своя папка памяти; `Edit` существующих файлов не ограничен |

Роли вне этой таблицы правило не трогает. Разбор — [permission-checklist](../checklists/permission-checklist.md).

Правило двустороннее по той же причине, что и `env`: инструмент Write можно заблокировать, а `cat > файл` пишет тот же файл мимо проверки. На живом прогоне выяснилось, что **платформа после блокировки Write сама предлагает агенту перейти на Bash** — так что односторонняя проверка здесь не просто дырява, а активно обходится по подсказке.

## Установка

### Плагином — ничего делать не нужно

Если методология установлена как плагин, хуки уже работают: `hooks/hooks.json` подключается автоматически при включении плагина. Проверить — командой из блока ниже.

### Вручную

```bash
# 1. Скопируй скрипты в свой проект — все, а не только guard.py:
#    конфигурация ссылается на четыре хука, а messages.py нужен каждому,
#    без него guard.py падает с ModuleNotFoundError ещё до первой проверки.
mkdir -p /path/to/your-project/.claude/hooks
cp hooks/*.py /path/to/your-project/.claude/hooks/

# 2. Подключи хуки в настройках проекта
#    Если .claude/settings.json уже есть — перенеси в него блок "hooks",
#    не затирая остальные ключи.
cp hooks/settings.example.json /path/to/your-project/.claude/settings.json
```

Два файла конфигурации отличаются только тем, откуда берётся путь к скрипту: `hooks.json` использует `${CLAUDE_PLUGIN_ROOT}`, `settings.example.json` — `${CLAUDE_PROJECT_DIR}`. Набор правил в них одинаковый, и тест это проверяет.

### Проверь, что защита встала — это обязательный шаг

Проверка идёт в два шага, и оба безопасны. Ни в одном из них нельзя проверять защиту опасной командой: смысл проверки в том, что хук может не работать, и тогда команда выполнится.

**Шаг 1 — работает ли сам скрипт.** Никакого риска: скрипт вызывается напрямую, ничего не выполняется.

```bash
echo '{"tool_name":"Bash","tool_input":{"command":"rm -rf /"}}' | python .claude/hooks/guard.py
```

Должен напечатать JSON с `"permissionDecision": "deny"`. Пусто или ошибка запуска — смотри раздел про интерпретатор ниже.

**Шаг 2 — подключён ли хук к сессии.** Попроси агента выполнить команду, которая заблокирована, но безобидна, если хук не сработает:

```bash
echo проверка > .env.check
```

Правило `env` обязано её заблокировать. Если вместо блокировки появился файл `.env.check` — скрипт работает, но не подключён: проверь конфигурацию и перезапусти сессию. Файл после проверки удали.

Проверка важна именно потому, что несработавший `PreToolUse` не останавливает команду. Хук, который не запустился, ведёт себя неотличимо от отсутствующего — с той разницей, что ты считаешь себя защищённым.

### Требования

Только Python 3.8+. Внешних зависимостей нет, всё на стандартной библиотеке.

**Имя интерпретатора — главный источник проблем при установке.** В конфигурациях указан `python`: так он называется в Windows. На macOS и большинстве Linux бинарника с таким именем нет, есть `python3`.

Выбрать имя автоматически статический JSON не позволяет, поэтому:

```bash
python3 --version   # если работает — поменяй "command" на python3
python --version    # если работает это — оставь как есть
```

Менять нужно **все вхождения**, а не только первое: в каждой конфигурации их десять, и они разбросаны по всем событиям. Поправишь один блок — `guard.py` заработает, а журнал, счётчик повторов и подсказка при старте останутся молчать, и это ничем себя не проявит.

```bash
# ручная установка
sed -i 's/"command": "python"/"command": "python3"/g' .claude/settings.json
```

```powershell
# то же в PowerShell
(Get-Content .claude\settings.json) -replace '"command": "python"', '"command": "python3"' |
  Set-Content .claude\settings.json -Encoding utf8
```

При установке плагином правится `hooks.json` внутри каталога плагина — но правку затрёт следующее обновление. Надёжнее задать `python3` доступным как `python`, например через `alias` в профиле оболочки или ссылку в `PATH`.

## Настройка под себя

Правила включаются списком, так что лишние можно не брать:

```json
"args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/guard.py", "--rules", "fs,git"]
```

Неизвестное имя правила хук не игнорирует, а отказывает с объяснением. Опечатка в конфигурации иначе молча отключила бы защиту — а хук, который не работает, но выглядит работающим, хуже отсутствующего.

Ролевая матрица правила `memory` задаётся словарём `MEMORY_MATRIX` в начале `guard.py`. Имя роли — это значение `agent_type`, то есть поле `name` из frontmatter агента.

Список клиентов БД для правила `sql` — константа `DB_CLIENTS` там же.

## Язык сообщений

Весь текст, который читает человек, живёт в одном файле — [`messages.py`](messages.py) — и существует на двух языках. Правила от языка не зависят: блокируется одно и то же, меняется только то, что написано в объяснении.

Язык выбирается в таком порядке:

1. переменная окружения `ABT_LANG` — `ru` или `en`;
2. файл `.claude/.abt-lang` в проекте, одно слово — его пишет скилл `setup-agent-team`;
3. английский.

```bash
# разово, для одной сессии
ABT_LANG=ru claude

# постоянно для проекта
mkdir -p .claude && printf 'ru\n' > .claude/.abt-lang
```

Английский стоит умолчанием потому, что плагин публичный: непонятный язык блокировки хуже понятного, а прочитать её нужно ровно тогда, когда что-то уже пошло не так. Русский при этом не «второй сорт» — методология написана на нём, и одна строка возвращает к нему весь человеческий текст.

Незнакомое значение (`ABT_LANG=de`) откатывается на английский и **не снимает защиту** — это проверяется тестом отдельно, потому что «опечатка в настройке молча отключила хук» здесь самый дорогой из возможных исходов.

Если язык не выбран, `session_start.py` один раз предложит его выбрать. После записи файла вопрос больше не возникает.

Добавляя сообщение, добавляй сразу оба языка: тест `TestMessageCatalogue` не пропустит ключ с одним переводом и не пропустит расхождение в наборе подстановок — иначе блокировка падала бы с `TypeError` ровно в тот момент, когда должна была сработать.

## Предложение развернуть команду

`session_start.py` — хук на `SessionStart`. Закрывает разрыв ожиданий: плагин ставит хуки и скиллы, но не роли, и после установки легко решить, что «ничего не включилось».

В проекте, где ролей методологии ещё нет, хук вкладывает в контекст короткую подсказку, и Claude сам предлагает сборку через `setup-agent-team`. В настроенном проекте **молчит**, и это не оптимизация: подсказка, повторяющаяся каждую сессию, тратит контекст и приучает себя игнорировать.

Наличие команды определяется по полю `name` во frontmatter, а не по имени файла: роль могли переименовать при адаптации.

Хук подключён к четырём матчерам — `startup`, `clear`, `resume`, `fork`, — то есть ко всем способам начать работу. Одного `startup` не хватало: после `/clear`, самого обычного «начать заново», подсказка не появлялась до полного перезапуска, и догадаться об этом было неоткуда. `compact` не подключён намеренно — он срабатывает посреди задачи.

Матчеры перечислены отдельными записями, а не альтернацией `startup|clear`: для `SessionStart` она не документирована, а матчер, тихо переставший совпадать, выключил бы подсказку молча.

Отключить навсегда — создать пустой файл `.claude/.no-team-setup-prompt`.

## Правило трёх попыток

`retry_guard.py` — механическая реализация правила 1 из [принципа 07](../principles/07-stop-rules.md). Подключён по умолчанию, работает на паре событий: считает неудачи на `PostToolUseFailure`, блокирует четвёртый слепой повтор на `PreToolUse`.

**Слепой повтор — это та же команда при том же состоянии файлов.** Если между попытками рабочая копия менялась, счётчик сбрасывается: прогон тестов, падающий три раза, пока агент чинит код, — нормальная работа, а не петля. Запретить её значило бы запретить цикл, который методология и поощряет.

Отпечаток рабочей копии считается только когда счётчик подошёл к пределу, чтобы не платить запуском `git` за каждый вызов инструмента.

Блокировка срабатывает **один раз** и отпускает. Дальше решение принимает человек: бесконечно блокировать команду хук не вправе.

Порог меняется флагом `--limit`.

## Журнал привилегированных действий

`approval_log.py` — хук на `PostToolUse` **и `PostToolUseFailure`**, реализация принципа 08. Подключён по умолчанию в обеих конфигурациях.

Два события, а не одно, потому что на живой установке проверено: падающая команда порождает `PostToolUseFailure`, а `PostToolUse` при этом **не приходит**. Пока хук висел только на успехе, журнал видел половину картины — заблокированный force-push и упавшая на середине миграция не оставляли следа вообще. Для аудита «попытался и не смог» обычно интереснее, чем «сделал». Исход записан в поле `ok`.

Он **дополняет** `guard.py`, а не дублирует: guard блокирует то, чего делать нельзя, а журнал записывает то, что делать можно, но стоит помнить — коммиты, пуши, миграции, установки пакетов, обращения к базе, правки чувствительных файлов.

Запись идёт в `.claude/approval-log.jsonl`, по строке на действие:

```json
{"at": "2026-08-27T11:15:05", "risk": "W", "what": "git-push", "detail": "git push origin main", "ok": true, "agent": "devops", "tool": "Bash", "session": "deadbeef"}
{"at": "2026-08-27T11:16:40", "risk": "P", "what": "db-access", "detail": "psql -c \"DELETE FROM users WHERE id = 1\"", "ok": false, "agent": "", "tool": "Bash", "session": "deadbeef"}
```

Пустое поле `agent` означает, что действие выполнено в главном потоке, а не ролью.

Метки в поле `what` — устойчивые идентификаторы и от языка сообщений не зависят. Журнал это запись, а не сообщение: если бы метки переводились, один файл после смены `ABT_LANG` содержал бы записи на двух языках, и по нему нельзя было бы ни искать, ни считать.

Посмотреть по-человечески:

```bash
python -c "import json,sys;[print(e['at'],e['risk'],e['agent'] or 'main',e['detail']) for e in map(json.loads,open('.claude/approval-log.jsonl',encoding='utf-8'))]"
```

**Рутина в журнал не попадает.** `ls`, `git status`, `git diff`, прогон тестов, правки обычных файлов — всё это отфильтровано намеренно: журнал, куда пишется всё подряд, читать никто не станет, и он перестанет быть журналом. Список того, что попадает, — константа `BASH_PATTERNS` в начале скрипта, дополняется одной строкой.

**Журнал стоит держать вне git.** В `detail` попадает текст команды, а в аргументах команд встречаются токены и пароли. Добавь `.claude/approval-log.jsonl` в `.gitignore`, если не уверен, что этого не случится.

Хук на `PostToolUse` не может ничего заблокировать и не должен: даже собственная ошибка записи не прерывает работу, а уходит в stderr.

Отключается удалением **обоих** блоков — `PostToolUse` и `PostToolUseFailure`. Убрать только первый недостаточно: записи о неудавшихся действиях, с текстами команд, продолжат идти в журнал.

## Stop-хук: не завершать работу с падающими тестами

`verify.py` — отдельный хук на событие `Stop`. Он делает условие готовности из `../checklists/implementation-path.md` обязательным: пока оно живёт только в тексте промпта, оно соблюдается по настроению.

Ставится **отдельно** и только вместе с командой проверки — без неё хук не знает, что запускать, и в поставку по умолчанию не входит. Добавь в `settings.json` рядом с блоком `PreToolUse`:

```json
"Stop": [
  {
    "hooks": [
      {
        "type": "command",
        "command": "python",
        "args": [
          "${CLAUDE_PROJECT_DIR}/.claude/hooks/verify.py",
          "--command", "pytest -q"
        ],
        "timeout": 300
      }
    ]
  }
]
```

Как ведёт себя:

- команда прошла — завершение разрешено;
- команда упала — завершение блокируется, агенту уходит вывод команды и запрет чинить симптом вместо причины;
- команда не уложилась в `--timeout` — считается непройденной и тоже блокирует: иначе достаточно подвесить тесты, чтобы снять гейт;
- команда падает подряд `--max-blocks` раз (по умолчанию два) — хук перестаёт блокировать, но требует прямо сказать пользователю, что задача не доведена;
- ошибка в аргументах хука — сообщение в stderr и **никакой** блокировки.

Два последних пункта — сознательные компромиссы в разные стороны. Бесконечная блокировка заперла бы сессию, когда агент починить не может; молчаливый пропуск вернул бы ровно ту проблему, ради которой хук и нужен. А опечатка в конфигурации не должна запирать работу вообще — в отличие от `guard.py`, где неверная конфигурация означает отказ, здесь цена блокировки выше цены пропуска.

Флаги: `--changed-only` пропускать проверку при чистой рабочей копии, `--timeout` предел выполнения, `--max-blocks` число блокировок подряд.

> `--changed-only` — оптимизация, а не поведение по умолчанию, и это намеренно. Штатный процесс заканчивается коммитом, после которого рабочая копия чистая: пропускай по умолчанию — и гейт отключится ровно в самом обычном сценарии.

## Тесты

```bash
python -X utf8 -m unittest discover -s hooks/tests
```

Больше полусотни тестов, и примерно половина из них проверяет, что хук **не** срабатывает: на `rm -rf ./build`, на `git push --force-with-lease`, на `git clean -n`, на `cat .env`, на `echo 'пример: > .env'`, на `grep` по слову `DELETE`. Это не формальность. Хук с ложными срабатываниями пользователь отключает в первый же день, и защиты не остаётся вовсе — так что ложное срабатывание здесь такой же баг, как пропущенная опасная команда.

Отдельная группа тестов — обходы, найденные триангулированным ревью: разделители команд (перевод строки, одиночный `&`), вложенный `sh -c`, вызов по абсолютному пути, присваивание перед командой, `WHERE` из подзапроса, выход из разрешённой зоны через `..`. Все они были рабочими дырами и закрыты.

Меняешь правило — добавляй оба теста: и на блокировку, и на разрешение.

## Чего эти хуки не делают

Честный список границ, чтобы не возникло ложного чувства защищённости.

- **Не заменяют матрицу разрешений.** `tools` в шаблоне агента — первая линия, хуки вторая. Убрать инструмент надёжнее, чем перехватывать его вызовы.
- **Не ловят обфускацию.** Команда, собранная из переменных или пропущенная через `base64 -d | sh`, проверку обойдёт. Вложенный `sh -c` раскрывается, но только на три уровня: дальше начинается уже не ошибка агента, а намеренное сокрытие. Хуки рассчитаны на первое, а не на противодействие злоумышленнику.
- **Покрывают перечисленный набор, а не весь деструктив.** `chmod -R 777 /`, `dd of=/dev/sda`, `git branch -D` под правила не попадают: это минимум из принципа 09, а не полный список опасных команд. Нужно больше — добавляй правила и тесты к ним.
- **Разбирают команду по правилам POSIX-оболочки.** Неэкранированный путь Windows (`C:\tools\app.exe`) теряет обратные слэши — но ровно так же его прочитает и сам Git Bash, через который команда выполняется. Пиши такие пути в кавычках или через прямые слэши.
- **`rm -rf` проверяется по списку опасных целей.** `rm -rf /usr` под правило не попадает: перечислить все системные пути нельзя, а блокировать любой абсолютный путь — значит получить хук, который мешает работать.
- **SQL проверяется только у известных клиентов БД.** Запрос через ORM, миграционный инструмент или собственный скрипт правило не увидит.
- **Правило `memory` опирается на `agent_type`.** В главном потоке этого поля нет, и правило там не применяется — это намеренно.

## Другие платформы

Идея переносима, механика — нет.

- **Cursor** — правил уровня pre-tool-call нет; ближайший аналог ограничений живёт в `.cursor/rules/` и остаётся уговором, а не механикой.
- **Codex / Cline / Aider** — перехват на уровне обёртки над вызовом инструмента, если она у тебя есть.
- **Собственный harness** — та же схема: обработчик перед выполнением, решение «разрешить/запретить» с объяснением.

Что переносится дословно: формат сообщения о блокировке из принципа 09 и правило «повторяющаяся ошибка становится кодом, а не новой строкой в промпте».
