# Обновление

Как обновить методологию в проекте, где она уже стоит, и что при этом нельзя затирать.

---

## Главное про обновления плагина

Две вещи, из-за которых обновление «не приходит», хотя всё сделано правильно.

**Сторонние маркетплейсы не обновляются сами.** Автообновление по умолчанию включено только у официальных маркетплейсов Anthropic. Для этого его нужно либо включить вручную, либо каждый раз обновлять каталог командой.

**Обновление видно только после подъёма версии.** Claude Code считает, что новая версия есть, когда в манифесте плагина изменилось поле `version`. Изменения, залитые без подъёма версии, до установленных плагинов не доедут.

---

## Обновить плагин

```
/plugin marketplace update sergvss
/reload-plugins
```

Первая команда обновляет каталог и подтягивает новую версию плагина, вторая применяет её без перезапуска.

> Здесь `sergvss` — **имя** маркетплейса, а не адрес репозитория. Адрес (`sergvss/agents-best-teams`) нужен только при первом добавлении. Разные идентификаторы, похожие на вид: `update` и `install` работают с именем, `add` — с адресом. Если `/reload-plugins` предупредит, что перечитает разговор, повтори с `--force`.

Чтобы не делать это руками каждый раз, включи автообновление: `/plugin` → вкладка **Marketplaces** → выбрать `sergvss` → **Enable auto-update**. После этого Claude Code проверяет обновления через несколько минут после старта сессии и предложит перезагрузить плагины, если что-то изменилось.

**Что обновится:** хуки, скиллы, документация — всё, что входит в плагин.
**Что не обновится:** роли в `.claude/agents/` вашего проекта. Их плагин не ставит, и обновлять их за вас не может — см. ниже.

---

## Обновить ручную установку

Копировать заново нужно не всё. Разница принципиальна: часть файлов вы адаптировали под проект, и перезапись сотрёт работу.

| Что | Обновлять | Почему |
|---|---|---|
| `hooks/*.py` | **да**, перезаписать | Код без вашей специфики: настройки проекта живут в `.claude/agents-best-teams.json`, и обновление его не трогает. Правили константы прямо в `guard.py` в старой версии — перенесите их в этот файл |
| `skills/` | **да**, перезаписать | То же самое |
| `.claude/settings.json` | **нет**, переносить руками | Там ваши настройки. Из нового `settings.example.json` перенесите только новые блоки хуков |
| `.claude/agents/` | **нет**, см. следующий раздел | Роли адаптированы под ваш стек |
| `.claude/agent-memory/` | **никогда** | Это накопленное знание ваших ролей, восстановлению не подлежит |
| `.claude/approval-log.jsonl` | **никогда** | Журнал действий |
| `.claude/.abt-lang` | **нет** | Выбранный язык сообщений хуков |
| `agents.config` | **нет** | Ваши модели и бюджеты |

```bash
cd <клон-репозитория-методологии>
git pull

PROJECT=/path/to/your-project
cp hooks/*.py "$PROJECT/.claude/hooks/"
cp -r skills/* "$PROJECT/.claude/skills/"
```

Затем откройте `hooks/settings.example.json` и свой `.claude/settings.json` рядом и перенесите то, чего у вас нет. В новых версиях появляются новые события, а не только новые правила: блок `PostToolUse` или `PostToolUseFailure` может отсутствовать у вас целиком.

## Что делать с адаптированными ролями

Самое неудобное место обновления, и честного автоматического решения у него нет.

Роли из `templates/` вы правили под свой проект: подставили стек, порты, зоны ответственности. Шаблоны в репозитории тоже меняются — добавляются поля frontmatter, уточняются формулировки, чинятся ошибки. Слить одно с другим может только человек.

Рабочий порядок:

```bash
# 1. Что изменилось в шаблонах с момента вашей установки
cd <клон-репозитория-методологии>
git log --oneline <ваша-версия>..HEAD -- templates/
git diff <ваша-версия>..HEAD -- templates/dev-backend.md
```

```
# 2. Перенести относящееся к делу в свою роль
```

Смотреть в первую очередь на:

- **новые поля frontmatter** — их обычно нужно просто добавить;
- **изменения в разделе «Что НЕ делает»** — это границы зоны, они важнее остального;
- **предупреждения со значком ⚠** — обычно означают, что без парного действия что-то работает не так, как выглядит.

Не переносить: блоки стека, порты, названия каталогов — там ваши значения.

Проще всего, если вы после установки закоммитили `.claude/` в свой проект: тогда видно, что вы правили, а что осталось шаблонным.

## Обновились с версии до 1.8.0 — выберите язык

Начиная с 1.8.0 хуки говорят на выбранном языке, и **умолчание английское**. Если раньше блокировки приходили по-русски, а после обновления стали английскими — ничего не сломалось, просто язык не задан:

```bash
mkdir -p .claude && printf 'ru\n' > .claude/.abt-lang
```

При первом запуске сессии плагин и сам предложит выбрать язык, если файла нет. Правила от языка не зависят — блокируется одно и то же.

При ручном обновлении не забудьте скопировать новый `hooks/messages.py`: без него хуки не запустятся вовсе, потому что импортируют из него весь свой текст.

## Обновились до 1.16–1.17 — что изменится в поведении

**Force-push, `reset --hard`, `git clean`, `DROP` и `TRUNCATE` больше не блокируются, а спрашивают вас** в окне подтверждения Claude Code. Жёстким отказом остались `rm -rf` по корню и переменной, SQL без `WHERE`, запись в `.env` и выход роли из зоны. В неинтерактивном запуске окна нет, и там это по-прежнему отказ. Разбор — [принцип 09](../principles/09-mechanical-invariants.md#отказ-или-подтверждение).

**После отказа auto mode агент спрашивает вас через меню вопросов**, а не пишет «выполните сами». Это работает само, с первого старта сессии после обновления: переносить ничего не нужно.

**У роли `qa-tester` появилась зона записи**, и держит её хук: тестовые файлы и системный временный каталог. Хук обновился вместе с плагином, а роль в вашем проекте — нет. Перенесите в неё из `templates/qa-tester.md`:

- раздел «Мутационная проверка: тест обязан краснеть» — теперь он велит ломать копию модуля, а не оригинал. Со старым текстом роль начнёт править продуктовый файл, и хук её остановит;
- две строки в «Что НЕ делаешь»: не править продуктовый код даже временно и не ставить зависимости;
- описание зоны в разделе памяти.

Зона узнаёт тесты по каталогам `tests`, `test`, `__tests__`, `spec` и по именам вроде `test_*.py`, `*.test.*`, `*.spec.*`. Тесты в проекте называются иначе — роль окажется заблокирована в собственных тестах. Добавьте свои каталоги или шаблоны имён в `.claude/agents-best-teams.json` — это работает и при установке плагином: [hooks/README.md](../hooks/README.md#файл-настроек-проекта).

**Рекомендованный состав внешних моделей сменился.** Ваш `agents.config` сам не обновится. Если в нём `google/gemini-3.7-flash`, посмотрите [замер на реальных дефектах](models.md#замер-на-своих-дефектах).

**Перезапустите открытые сессии.** Хуки подхватываются при старте, и до перезапуска работают прежние.

## Обновились до 1.20 — шлюз ревью для коммитов

**Шлюз ревью для коммитов.** С 1.22.0 он выключен по умолчанию и включается пустым файлом `.claude/.review-gate`; нужна и роль `code-reviewer`. В 1.20–1.21 он включался сам при наличии роли. Разбор — [hooks/README.md](../hooks/README.md#шлюз-ревью-для-коммитов-кода).

Чтобы окно не открывалось после настоящего ревью, роль должна уметь закреплять одобрение. Роль в вашем проекте сама не обновится — перенесите в неё из `templates/code-reviewer.md` раздел «Одобрение для шлюза коммитов». Без него ревью будет проходить как раньше, но окно будет открываться и после него.

**Stop-хук `verify.py`** включается записью `{"<путь к проекту>": "<команда тестов>"}` в файле пользователя `~/.claude/agents-best-teams/verify.json`: плагин подключает хук сам, и прописывать путь к `verify.py` не нужно. Блок `Stop` с `--command`, если он у вас уже есть, продолжает работать. Напоминания при старте сессии с 1.22.1 нет.

**Ручная установка:** скопируйте `hooks/*.py` заново — появился `review_gate.py` — и перенесите из `hooks/settings.example.json` три новые записи `review_gate.py`: две в `PreToolUse` и одну в `PostToolUse`.

## После обновления — проверить

Обновление хуков меняет то, что блокируется. Прогоните хотя бы второй уровень из [verification.md](verification.md): пять минут, и вы знаете, что защита действительно работает, а не просто лежит на диске.

Минимум:

```bash
# Хук отвечает
echo '{"tool_name":"Bash","tool_input":{"command":"rm -rf /"}}' | python .claude/hooks/guard.py
```

Ожидается JSON с `"permissionDecision": "deny"`. Пусто или ошибка запуска — смотрите [hooks/README.md](../hooks/README.md#требования), скорее всего дело в имени интерпретатора.

## Для тех, кто ставил до версии 1.0.0

До 1.0.0 методология была только текстом: принципы, шаблоны, чек-листы. Ничего из этого не сломалось — шаблоны работают как раньше.

Что появилось и чего у вас нет:

1. **Защитные хуки** — раньше принцип 09 описывал их как идею, теперь это рабочий код. Ставится вместе с плагином или копированием, см. [install.md](install.md).
2. **Чек-листы стали скиллами** — содержимое то же, но теперь Claude подтягивает их сам, когда они уместны.
3. **Одиннадцатый принцип** — недоверенный ввод.
4. **Поля frontmatter в ролях** — `permissionMode`, `maxTurns`, `effort`, `memory`. Их нужно перенести в свои адаптированные роли вручную.
5. **Выбор модели по порогу, а не по тиру** — если у вас есть `agents.config`, сверьте его с [models.md](models.md): таксономия `top/strong/mid/light` больше не используется.

Отдельно: поле `memory` у пяти ролей работает **только вместе с защитным хуком**. Включите его без хука — и роли получат Write и Edit в обход своего списка инструментов. Разбор — в [permission-checklist](../checklists/permission-checklist.md).

## Автору методологии: как выпускать обновление

Чтобы обновление доехало до установленных плагинов:

1. Подними `version` в `.claude-plugin/plugin.json` **и** в `VERSION` — CI проверяет, что они совпадают.
2. Опиши изменения в `CHANGELOG.md`.
3. Запушь в `main`.
4. Поставь тег и опубликуй его:

```bash
git tag -a v1.2.0 -m "Одной строкой: что в этом выпуске"
git push origin v1.2.0
```

Без первого пункта изменения в репозитории есть, а у пользователей их нет.

**Пятый пункт, без которого предыдущие четыре ничего не гарантируют:**

```bash
claude plugin marketplace update sergvss && claude plugin update agents-best-teams
claude plugin list
```

Статус обязан быть рабочим, а не `✘ failed to load`.

Причина отдельного пункта: `claude plugin validate` **не проверяет загрузку**. Версия 1.9.2 вышла ровно из-за этого — манифест объявлял стандартный `hooks/hooks.json`, который Claude Code подхватывает сам, дубль отвергал загрузку всего плагина, и при этом `validate` печатал `✔ Validation passed`, установка печатала `Successfully installed`, а CI был зелёный. Единственное место, где поломка видна, — `claude plugin list`.

Правило общее: **успешная валидация и успешная установка не являются доказательством того, что плагин работает.** Доказательство — статус в списке установленных.

Без четвёртого всё работает, но теряются две вещи: пользователю не на что сослаться при отчёте о проблеме («на v1.1.2 не воспроизводится»), и на GitHub не появляется страница Releases, по которой видно историю выпусков без чтения коммитов.

Версия в бейдже README читается из манифеста автоматически — отдельно её обновлять не нужно.

**Два README.** По умолчанию GitHub показывает [`README.md`](../README.md) — он английский; русский лежит в [`README.ru.md`](../README.ru.md), переключатель бейджами в шапке обоих.

Правило сопровождения после того, как английский стал основным: **отставать разрешено только `README.ru.md`**. То, что видит посетитель репозитория первым, обязано быть верным — расхождение по фактам не допускается ни в какую сторону, а вот запаздывание перевода на выпуск допустимо только у русской версии. Разделы, которых в английской версии нет намеренно (благодарности целиком, «Когда команда нужна»), сверять не нужно.

Правил разделы «Установка», «Обновление» или «Что включается когда» — перенеси правку в оба файла в том же коммите.

## Автору методологии: публикация в community-маркетплейс

Каталог `anthropics/claude-plugins-community` — публичный маркетплейс, куда попадают сторонние плагины после ревью. Пользователи подключают его как `/plugin marketplace add anthropics/claude-plugins-community` и ставят из него с суффиксом `@claude-community`.

**Подача идёт через форму, не через PR и не через CLI:**

- Console: [platform.claude.com/plugins/submit](https://platform.claude.com/plugins/submit)
- claude.ai: [claude.ai/admin-settings/directory/submissions/plugins/new](https://claude.ai/admin-settings/directory/submissions/plugins/new) — требует организации Team или Enterprise с доступом к управлению каталогом. Индивидуальному автору нужна форма Console.

Перед подачей прогнать локально то же, что запускает пайплайн ревью:

```bash
claude plugin validate .
```

Ожидается `✔ Validation passed` или `✔ Validation passed with warnings` — предупреждения подачу не валят. Флаг `--strict` делает их ошибками; у нас CI гоняет именно со `--strict`. Кроме валидации пайплайн прогоняет автоматический скрининг безопасности.

**Как узнать, что опубликовали.** Одобренный плагин закрепляется в каталоге на конкретный commit SHA, дальше CI сам двигает эту привязку по мере пушей в репозиторий. Публичный каталог синхронизируется с пайплайном ревью **раз в сутки**, поэтому между одобрением и появлением в маркетплейсе есть задержка. Проверять по имени плагина здесь: [`.claude-plugin/marketplace.json` в claude-plugins-community](https://github.com/anthropics/claude-plugins-community/blob/main/.claude-plugin/marketplace.json). Пока имени в этом файле нет — установить из community-каталога нельзя.

Второй маркетплейс, `claude-plugins-official`, курируется Anthropic отдельно: состав определяют они, процедуры подачи не существует, и форма выше в него не ведёт.

### Что вписать в форму

Собрано заранее, чтобы не сочинять в момент подачи.

| Поле | Значение |
|---|---|
| Репозиторий | `https://github.com/sergvss/agents-best-teams` |
| Имя плагина | `agents-best-teams` |

| Автор | sergvss |

Описание — то же, что в манифесте, чтобы карточка и `/plugin` не расходились:

Последнее предложение убирать не стоит: содержимое действительно русское, и человек, узнавший об этом после установки, поставит плохую оценку заслуженно.

### Что стоит знать про скрининг безопасности

Плагин ставит исполняемый код, поэтому его будут смотреть. Наши ответы на очевидные вопросы:

- **Сети нет.** Ни в одном хуке нет `urllib`, `socket` или `requests` — проверяется тестом.
- **`eval`, `exec`, `os.system` не используются** — тоже тестом.
- **Внешних зависимостей нет**: только стандартная библиотека Python, ни `requirements.txt`, ни `package.json`.
- **`subprocess` вызывается в трёх хуках.** `git status --porcelain` в `retry_guard.py` и `verify.py` — чтобы отличить слепой повтор от осмысленного. `review_gate.py` вызывает только чтение git (`diff`, `ls-files`, `hash-object` без `-w`, `config --get`) — списком аргументов, без оболочки. И в `verify.py` с `shell=True` запускается команда проверки — **та, что пользователь сам записал** в свой файл `~/.claude/agents-best-teams/verify.json` или в аргумент хука. Файл лежит вне репозитория, поэтому склонированный проект команду не подложит. Без записи хук ничего не запускает, а запись агентом идёт только через окно подтверждения.
- **Секретов и личных путей в репозитории нет** — проверяется на каждом прогоне тестов, а не разово перед подачей.

### Перед тем как жать «отправить»

```bash
python -X utf8 -m unittest discover -s hooks/tests   # тесты, включая проверку на утечки
claude plugin validate .                             # то же, что гоняет пайплайн
claude plugin list                                   # статус обязан быть ✔ enabled
```

Третья команда здесь не формальность: подавать плагин, который не загружается, — ровно то, что чуть не случилось в версии 1.9.2.
