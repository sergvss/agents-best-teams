# Работа в ветке: начало и завершение

Задача Tier 2 и выше идёт в отдельной ветке, а не прямо в основной. Основная ветка остаётся рабочей всё время, пока идёт задача. Откат неудачной работы — это удаление ветки, а не раскопки в истории. Влить работу в основную решает человек, выбором в меню, а не агент по факту зелёных тестов.

Tier 1 — правка в одну-две строки — делается на текущей ветке: отдельная ветка ради неё стоит дороже самой правки.

---

## Начало

Когда: перед первой правкой кода задачи Tier 2 и выше.

1. **Узнай текущую и основную ветку.** Текущая — `git branch --show-current`. Основная — `git symbolic-ref --short refs/remotes/origin/HEAD` без префикса `origin/`; нет удалённого репозитория — `main` или `master`, какая есть.
2. **Уже не на основной** — работай здесь: ветку для задачи кто-то уже выбрал.
3. **На основной** — прочитай политику проекта: `git config --get abt.branches`.
   - `auto` — создай ветку, не спрашивая.
   - `off` — работай в основной: пользователь так решил.
   - Пусто — **заведи ветку сразу** и одним вопросом спроси пользователя: «Работать в отдельных ветках и дальше? Да — запомню и буду создавать ветку сам. Нет — работаю в основной». Ответ запиши: `git config abt.branches auto` или `git config abt.branches off`. Это настройка этого репозитория, она не попадает в коммиты.
   - Ветка до ответа, а не ожидание ответа: ветка обратима, и основная остаётся чистой, даже если ответа не будет. Живой прогон показал: «остановись и спроси» в безголовой сессии превращается в «сделал всё в основной, спросил в конце». Ответят «нет» — `git switch <основная>`, незакоммиченные правки вернутся.
   - Ты субагент — вопрос верни в отчёте блоком «НУЖНО РАЗРЕШЕНИЕ», а ветку заведи.
4. **Имя ветки** — `<тип>/<короткое-имя>`: `feat/`, `fix/`, `refactor/`, `docs/`, `chore/`. Пример: `fix/content-length`.
5. **`git switch -c <имя>`.** Незакоммиченные правки переедут в новую ветку вместе с тобой. Если среди них есть чужие, не включай их в свои коммиты — принцип 07, правило 5.
6. **Запиши в ledger**, если он заведён: «ветка: `<имя>`, основная: `<имя>`». Продолжающий задачу должен знать, где она живёт.

### Worktree — только когда одну область трогают двое

По умолчанию роли разводят зоны: у каждого каталога ровно один хозяин (`../docs/claude-code-mechanisms.md`, «Worktree против зон ответственности»). Worktree — отдельный рабочий каталог со своей веткой — нужен, только когда зоны не помогают:

- две роли меняют одну и ту же часть кода параллельно;
- два подхода к задаче делаются на сравнение;
- рискованный эксперимент может не пригодиться.

Как: для роли — изоляция worktree при её вызове (в Claude Code параметр `isolation: "worktree"`); для своей сессии — встроенный инструмент платформы (в Claude Code — `EnterWorktree`). Не `git worktree add` руками: worktree, созданный в обход платформы, она не видит и не убирает. Worktree создаётся от основной ветки, а не от твоего HEAD: незакоммиченные правки в него не попадут.

## Завершение

Когда: работа в ветке готова и её надо влить, отправить или отложить.

1. **Полный набор тестов проекта зелёный.** Не один свой файл, а весь набор. Красный — покажи падения и остановись: недоделанную работу не вливают.
2. **Ревью пройдено**, если его требует Tier (`implementation-path.md`, шаг 5). Включён шлюз ревью — коммит кода без одобрения `code-reviewer` откроет окно.
3. **Незакоммиченные правки** — покажи `git status --short` и спроси, коммитить ли. Коммит делается по просьбе пользователя (`implementation-path.md`, шаг 8), и меню ниже — подходящий момент спросить.
4. **Меню — одним сообщением, выбирает пользователь:**
   1. Слить в `<основная>` локально
   2. Отправить ветку и открыть pull request
   3. Оставить ветку как есть

   Ты субагент — меню не показывай: верни его в отчёте, спросит главный диалог.
5. **Слить:**
   - `git switch <основная>`; есть удалённый репозиторий — `git pull --ff-only`;
   - `git merge --no-ff <ветка>`;
   - полный набор тестов на результате слияния. Красный — остановись, ветку не удаляй, покажи падения;
   - зелёный — `git branch -d <ветка>` и уборка worktree, если его создавал ты. Именно `-d`, не `-D`: `-d` откажет, если в ветке осталось неслитое.
6. **Pull request:**
   - `git push -u origin <ветка>`;
   - открыть PR средствами платформы (например, `gh pr create`) и дать ссылку;
   - ветку и worktree не трогать: они нужны, пока PR открыт.
7. **Оставить** — назови ветку и где лежит worktree. Больше ничего не делай.

## Запреты

- **Удалить ветку с неслитой работой** — только если пользователь сам написал «удалить». На `git branch -D` и `git worktree remove --force` защитный хук откроет окно подтверждения.
- **Никогда `--force` по своей инициативе.** Отклонённый push значит, что удалённая ветка ушла вперёд. Разберись — `git fetch`, `git log` — а не перезаписывай.
- **Не сливай в основную без выбора пользователя** в меню. Зелёные тесты — условие слияния, а не разрешение на него.
- **Не трогай чужие worktree** — только созданные в этой задаче.
