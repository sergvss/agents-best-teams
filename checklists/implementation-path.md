- [ ] Прочитал MEMORY.md своего агента (контекст из прошлых сессий)

- [ ] Определил Tier (1 / 2 / 3) — см. `planning-checklist.md`
- [ ] Для Tier 3 — сформировал письменный план и показал пользователю
- [ ] Правка крупнее пары строк на основной ветке — завёл ветку для задачи (`branch-workflow.md`, «Начало»). Политика проекта — в `git config abt.branches`; не задана — ветка сразу и один вопрос пользователю, работать ли так дальше

## Шаг 2: реализация

Баг или новая логика — **тест сначала** (`test-first.md`): красный тест, проверка, что он падает по нужной причине, потом код. Непонятно, почему ломается, — **отладка от корня** (`debugging.md`) до исправления.

### Tier 1 (делаю сам)
- [ ] Прочитал затронутые файлы
- [ ] Внёс минимальные хирургические правки
- [ ] Проверил что ничего не сломал смежного

### Tier 2-3 (делегирую)
- [ ] Сформулировал ТЗ по HANDOFF-шаблону для каждого агента
- [ ] Запустил агентов (параллельно или последовательно по зависимостям)
- [ ] Слежу за бюджетом делегаций (Tier 2: 6, Tier 3: 20; делегация — каждый вызов роли, включая повторное ревью). Это интервал **до чекпоинта**, а не потолок: дошёл до числа — доложил и спросил, продолжать ли, а не остановился навсегда

---

## Шаг 3: проверка инвариантов

После реализации, до QA:

- [ ] **API-контракт:** новые эндпоинты следуют принятому соглашению
- [ ] **Авторизация:** правильные guards на новых эндпоинтах
- [ ] **Миграции:** схема БД меняется только через систему миграций, не в runtime
- [ ] **Scope:** затронуто только то, что относится к задаче (нет «улучшений» рядом)
- [ ] **`.env`:** не в diff, нет захардкоженных секретов в коде
- [ ] **Формат ошибок:** единый через глобальные handlers

## Шаг 5: ревью

**Ведёшь задачу сам, без оркестратора, — шаг всё равно твой.** Этот шаг чаще всего теряется молча: в роли `pm-orchestrator` он прописан, а главный агент, взявший задачу на себя, его пропускает. Так в живом проекте ушёл десяток коммитов кода без единого ревью, и регрессия дошла до владельца. Сам себе ты ревьюером не будешь — вызови `code-reviewer` там, где его требует Tier (ниже).

Механическая страховка — шлюз ревью: коммит кода без одобрения `code-reviewer` открывает человеку окно. В Claude Code это `../hooks/review_gate.py`; он выключен по умолчанию и включается файлом `.claude/.review-gate`. Окно — не повод отвечать «да» по привычке: если ревью было, оно закрепляется одобрением, и окна нет.

Ревьюеру передаётся **ТЗ** — задача пользователя и критерии приёмки. Ревью идёт в два этапа: сначала «сделано то?», потом «сделано хорошо?» (шаблон `code-reviewer`).

**Tier 1:** не нужно.

**Tier 2:**
- [ ] `code-reviewer` (PRIMARY) — если security / RBAC / API-контракт / миграции
- [ ] Если задача из списка выше — **+ SIDE-A** (одна внешняя модель из `agents.config`). Не «при необходимости»: для security, RBAC, API-контракта и миграций второе независимое мнение обязательно. SIDE-B на Tier 2 не запускается — обоснование в `../principles/04-orchestration-budgets.md`

**Tier 3:**
- [ ] `code-reviewer` (PRIMARY) — обязательно
- [ ] SIDE-A + SIDE-B параллельно — триангуляция, **если они настроены** (см. `../principles/05-triangulated-review.md`). Если нет — отметить в отчёте, что внешнего мнения не было
- [ ] Применено правило 2-из-3 для блокеров. Находки SIDE-моделей пересортировать по достижимости в этом продукте: внешний ревьюер ранжирует по тяжести механизма, а не по тому, случится ли это у пользователя

## Шаг 6: итерация (если есть замечания)

**Сначала проверь замечание, потом чини.** Ревьюер — особенно внешняя модель без контекста проекта — ошибается уверенно. За неделю живых прогонов этой методологии примерно половина блокеров внешних моделей оказалась ложной: «запись не узнаётся» — тест показал, что узнаётся; «первый коммит упадёт» — тест проходит. Починка ложного замечания — лишняя правка, лишнее ревью и иногда новый баг.

- [ ] Каждое замечание сверено с кодом: воспроизведено тестом, найдено в файле или опровергнуто
- [ ] Ложное — отклонено **с доводом** (что проверено и что показало), а не молча и не из вежливости
- [ ] Неясное — переспрошено, а не угадано
- [ ] Без «вы абсолютно правы» и «отличное замечание»: согласие — это правка, а не фраза
- [ ] В отчёте — список отклонённых замечаний с причиной: человек должен видеть, что отвергнуто
- [ ] Блокеры 🔴 — исправить обязательно перед мержем
- [ ] Замечания 🟡 — взвесить, договориться с пользователем
- [ ] После правок — повторный прогон QA (точечно по изменённым частям)
- [ ] Повторное ревью — узкое: ревьюеру прошлые замечания и отчёт о правке, а не «посмотри всё заново». Находки в нетронутом коде — в отчёт человеку, новый раунд они не открывают (шаблон `code-reviewer`, «Повторное ревью после правки»)
- [ ] Третий раунд «ревью → правка» по задаче, а блокеры остались — стоп и доклад пользователю, четвёртого раунда нет (`../principles/07-stop-rules.md`, правило 7). Исполнитель упёрся в сложность, а не в разное понимание задачи, — предложи человеку вариант «ещё раунд на более сильной модели»

## Шаг 9: отчёт пользователю

**Утверждение без доказательства в отчёт не идёт.** Каждое «готово» опирается на вывод команды, запущенной в этом же ходе после последней правки, а не на память и не на слова роли.

| Утверждение | Чем доказать | Не доказывает |
|---|---|---|
| Тесты проходят | вывод команды тестов всего набора: число тестов, 0 провалов | «должны пройти», прогон до последней правки, прогон одного файла |
| Баг исправлен | тест, воспроизводящий баг: красный до исправления, зелёный после | зелёный тест, который не краснел |
| Роль выполнила задачу | `git diff` по её файлам и её отчёт с командами и выводом | «готово» в отчёте роли |
| Требования выполнены | построчная сверка с ТЗ | зелёные тесты |
| Сборка или линтер чистые | вывод команды с кодом 0 | «тесты прошли» |

Слова «готово», «всё работает», «отлично» до вывода команды — признак, что проверки не было.

## Сигналы, что что-то пошло не так

| Сигнал | Что делать |
|---|---|
| Задача расползается >15 шагов | Переклассифицировать в Tier 3, чекпоинт |
| Агент вышел за зону | Остановить, переформулировать ТЗ |
| Hook заблокировал команду | Не обходить, прочитать причину, попросить пользователя |
| 3 retry подряд не сработали | Стоп, доложить с альтернативами |
| Внешний сервис падает 2+ раз | Стоп, сообщить о деградации |
| 70% контекста заполнено | Чекпоинт, возможно продолжить в новой сессии |
