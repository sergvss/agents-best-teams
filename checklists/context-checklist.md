# Чек-лист: управление контекстом в команде агентов


---

## Проблема контекста в команде

В команде агентов контекст — дефицитный ресурс на каждом уровне:
- Оркестратор тратит контекст на координацию
- Каждый subagent тратит контекст на свою задачу
- При передаче задачи (HANDOFF) часть контекста теряется

Без управления контекстом агент к концу длинной задачи «забывает» начало — и начинает принимать решения без важной информации.

---

## Перед стартом задачи

- [ ] Прочитал MEMORY.md своего агента (институциональное знание из прошлых сессий)
- [ ] Прочитал только релевантные файлы, а не «всё подряд»
- [ ] Для Tier 3: прочитал README + PROJECT_MAP + CHANGELOG — источники истины проекта
- [ ] Большие файлы читаю с `limit:`, не целиком

---

## Во время работы

### Контроль объёма вывода

- [ ] Bash stdout > 500 строк → не выводить целиком, использовать `| head`, `grep`, `wc -l`
- [ ] Логи → `tail -100`, не `cat`
- [ ] `git diff` большого коммита → сначала `--stat`, потом точечно по файлам
- [ ] SQL-запросы → `LIMIT 50`

### Порядок важнее объёма

- [ ] Стабильное — в начало, изменчивое — в конец. Это не эстетика: кэш промптов работает по общему префиксу, и одна изменившаяся строка вверху обесценивает всё, что ниже
- [ ] Не переставляю блоки контекста между вызовами без нужды — тот же набор в другом порядке это другой префикс

Разбор экономики — `../principles/04-orchestration-budgets.md`, раздел о кэшировании.

### Сигналы перегрузки контекста

- [ ] Если агент начинает «забывать» инструкции из начала задачи — сигнал 70% заполнения
- [ ] При 70% → чекпоинт (зафиксировать прогресс) → продолжить в новой сессии или сейчас с кратким резюме
- [ ] Не пытаться «дотянуть» задачу при полном контексте — качество деградирует

---

## При HANDOFF (передаче задачи субагенту)

- [ ] ТЗ по HANDOFF-шаблону — контекст + задача + что читать + constraints + acceptance criteria
- [ ] Явно указано «что прочитать перед правкой» — не заставлять агента тратить контекст на поиск
- [ ] ТЗ не копирует весь контекст оркестратора — только то, что нужно для конкретной подзадачи
- [ ] Если агент работает с большой кодовой базой — указываю конкретные файлы, не «посмотри что-нибудь»

---

## Persistent memory — граница с оперативным контекстом

- [ ] Долгосрочное знание (инварианты, gotchas, конвенции) → MEMORY.md (между сессиями)
- [ ] Текущий прогресс задачи → Todo/Plan (в рамках сессии)
- [ ] Не путаю эти два вида хранения

### Что писать в MEMORY.md vs что держать в контексте

| Тип информации | Куда |
|---|---|
| «Этот файл нельзя трогать, потому что...» | MEMORY.md |
| «Миграция X сломается, если...» | MEMORY.md |
| «Следующий шаг задачи — Y» | Todo/Plan в сессии |
| «Нашёл баг Z, нужно исправить» | Todo/Plan (и передать dev-агенту) |
| Токены, пароли, ключи | Никуда — очистить сразу |

---

## После завершения задачи

- [ ] Обновил MEMORY.md агента новыми находками (если крупная задача)
- [ ] Очистил чувствительные данные из контекста и storage (особенно browser-tester)
- [ ] Если сессия была длинной — триггер на кьюрирование MEMORY.md

## Стиль прозы в отчётах и ТЗ

Человек в команде агентов не делает работу, а проверяет её: читает подряд отчёты нескольких ролей — три ревью при триангуляции, отчёты `qa-tester`, диагноз `investigator`. Скорость чтения становится узким местом. Просьба «пиши короче» работает плохо: правило оценочное, и через пару ответов модель возвращается к прежнему стилю.

Работают измеримые правила. Основа — принципы ASD-STE100 (Simplified Technical English, стандарт контролируемого языка авиационной документации), примерно на 80%, на языке проекта:

- [ ] Сначала вывод, потом детали.
- [ ] Предложение не длиннее 20 слов.
- [ ] Один термин — одно значение, без синонимов для разнообразия.
- [ ] Активный залог: названо, кто или что действует («скрипт удаляет файл», а не «файл удаляется»).
- [ ] Не больше трёх существительных подряд.
- [ ] Без вступлений, пересказа задачи и пустых оговорок.

**Границы.** Правило касается прозы, а не структуры: JSON внешнего ревьюера, таблицы и шаблоны отчётов остаются как есть. Оговорка остаётся, если она меняет решение — риск, условие, исключение; убирается только пустая. Словарь STE (около 900 слов) не применяется: модель его не помнит, а для русского он не работает — берутся только принципы.

**Эскалация.** Человек пишет «не понял», «подробнее», «шире» — роль раскрывает тему: контекст, пример, аналогия. Короткие предложения и единые термины сохраняются и тогда.

**Замер.** `code-reviewer` четыре раза ревьюил один и тот же коммит из двух слоёв, по два прогона без правила и с ним. С правилом отчёт короче на 18%, предложение — на 27% (8,4 слова против 11,5), доля предложений длиннее 20 слов упала с 6% до 1%. Существенные находки не потерялись: четыре из пяти известных в каждом прогоне обоих вариантов. Выборка маленькая, результат предварительный. Важная деталь постановки: если правило уже стоит в глобальных инструкциях пользователя, вариант «без правила» его тоже получает, и замер ничего не показывает — первая попытка так и испортилась.

## Размер контекста по ролям агентов

Разные агенты требуют разного объёма контекста:

| Агент | Типичный контекст | Почему |
|---|---|---|
| pm-orchestrator | Средний | Координация, не детали реализации |
| dev-backend / dev-frontend | Большой | Нужно читать много файлов для понимания |
| code-reviewer | Большой | Читает diff + полные файлы |
| qa-tester | Средний | Тесты + API-контракт |
| browser-tester | Малый | Сценарий + URL, детали не нужны |
| docs-writer | Малый | Читает документацию, не код реализации |

Это влияет на планирование: для long-running задач dev-агентов закладывай чекпоинты.
