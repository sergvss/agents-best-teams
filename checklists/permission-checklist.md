# Чек-лист: матрица разрешений агентов


---

## Принцип минимальных привилегий

Каждый агент получает **только те инструменты, которые нужны для его роли**. Не «на всякий случай», не «может пригодиться».

Почему это важно:
- Агент с `Edit` не будет случайно редактировать код, если это не его задача
- Ревьюер без `Edit/Write` физически не может «помочь» вместо того, чтобы передать задачу
- Ограниченный набор инструментов — документация роли сама по себе

**Ключевые ограничения по умолчанию:**
- `pm-orchestrator` и `code-reviewer` — без Edit/Write (не пишут код, физически не могут)
- **Роли-аналитики** — `security-reviewer`, `investigator`, `design-reviewer`, `scope-challenger` — тоже без Edit/Write. Они смотрят, ставят диагноз и передают профильной роли. `investigator` не пишет даже тест на воспроизведение: условия он описывает, тест пишет `qa-tester`
- **Финансовые роли** — `finops-engineer`, `unit-economics-analyst`, `investment-analyst`, `vendor-auditor` — тоже только читают. Они считают и передают вывод человеку: правки инфраструктуры делает `devops`, зависимости — профильный dev-агент. Отдельно про `investment-analyst`: продуктовых файлов он не касается вовсе, его источники — метрики и выгрузки
- `devops` и `local-sysops` — без Write (только Edit существующих файлов, не создают новые без согласования)
- `browser-tester` — запись только внутри каталога E2E: подойдёт и `e2e/` в корне, и `tests/e2e/`. Внутри зоны открыты **все** инструменты записи, за её пределами — ни один. Юнит-тесты чужой зоны (`server/tests/`, `client/tests/`) закрыты: ими владеет `qa-tester`. Каталог с другим именем (`cypress/`, `playwright/`) в зону не входит — это константа `BROWSER_TESTER_WRITE_SEGMENTS` в `../hooks/guard.py`, правится под проект.

  Граница проводится по файлам, а не по инструментам, и это не мелочь. Раньше `Edit` был закрыт роли везде, включая её собственную зону: чтобы поправить одну строку в спеке, приходилось переписывать файл целиком через `Write`. Правило требовало **более разрушительной операции вместо точной** — ровно того, против чего написан весь этот чек-лист
- `external-llm-reviewer` — только Bash (вызов CLI-обёртки над внешним LLM API), ничего не пишет в репозиторий — отчёт возвращает в stdout

## Матрица режимов

Список инструментов отвечает на вопрос «что агент может». Эта таблица — на вопрос «на каких условиях». Оба набора вместе описывают роль целиком; поодиночке — нет.

| Агент | permissionMode | maxTurns | effort | memory |
|---|---|---|---|---|
| pm-orchestrator | default | 30 | high | project + хук |
| code-reviewer | default | 20 | high | project + хук |
| dev-backend | acceptEdits | 30 | medium | project |
| dev-frontend | acceptEdits | 30 | medium | project |
| dev-database | acceptEdits | 25 | high | project |
| qa-tester | acceptEdits | 30 | medium | project |
| browser-tester | acceptEdits | 40 | medium | project + хук |
| devops | default | 25 | high | project + хук |
| local-sysops | default | 15 | low | project + хук |
| docs-writer | acceptEdits | 20 | low | project |
| i18n-keeper | acceptEdits | 25 | low | project |
| security-reviewer | default | 25 | high | project + хук |
| investigator | default | 30 | high | project + хук |
| design-reviewer | default | 20 | medium | project + хук |
| scope-challenger | default | 15 | high | project + хук |
| finops-engineer | default | 20 | medium | project + хук |
| unit-economics-analyst | default | 15 | high | project + хук |
| investment-analyst | default | 25 | high | project + хук |
| vendor-auditor | default | 20 | medium | project + хук |
| external-llm-reviewer | — | — | — | — |

Что означает каждая колонка:

- **permissionMode** — `acceptEdits` у тех, чья обычная работа состоит из правок класса D (`../principles/03-risk-classes.md`: правки в репозитории обратимы через git). `default` остаётся у `devops` — он ближе всех к операциям класса P: релизы, теги, запуск сервисов. Править `.env` ему при этом нельзя, как и всем: правило `env` роль не различает вовсе; у `local-sysops` по правилу «не уверен — бери строже»; и у десяти ролей без Edit/Write, где поле всё равно ни на что не влияет — это все, кто только смотрит и считает.
- **maxTurns** — бюджет шагов из `../principles/04-orchestration-budgets.md`. Раньше был просьбой в промпте, теперь ограничение механическое. Низкое значение у узких ролей осмысленно само по себе: длинная цепочка у `local-sysops` — это сигнал, что он вылез за свою зону.
- **effort** — регулятор стоимости, независимый от выбора модели. `high` там, где цена ошибки выше цены прогона (ревью, схема БД, релиз). `low` там, где задача механическая (переводы, документация).
- **memory** — persistent memory из `../principles/06-memory-hygiene.md`. Про пометку ⚠ — следующий раздел.

### Чего permissionMode не делает

Колонку выше соблазнительно прочитать как «механическая реализация классов риска». Это неверно, и различие принципиальное.

Точные формулировки из документации:

- `default` — спрашивает при **первом использовании каждого инструмента**, а не на каждое действие. После первого «да» правки идут без вопросов.
- `acceptEdits` — авто-принимает правки файлов и обычные файловые команды (`mkdir`, `touch`, `mv`, `cp`) для путей в рабочей директории. Произвольный Bash под него не попадает.

Отсюда два следствия:

- **Класс W** (применение миграций, `git commit`, глобальные установки) выполняется через Bash, и `permissionMode` им не управляет вообще.
- **Класс P** (`git push --force`, DDL на проде, правка `.env`) требует переподтверждения **каждый раз** — режима с такой семантикой среди значений `permissionMode` просто нет.

`permissionMode` задаёт базовый уровень трения, и только. Классы W и P закрываются правилами разрешений и защитными хуками — `../principles/09-mechanical-invariants.md`. Пока хуков нет, эти два класса держатся на тексте промпта, то есть на уговорах.

### Автоматический режим меняет не защиту, а заметность

Хуки от режима разрешений не зависят: заблокированное остаётся заблокированным и в `bypassPermissions`, и в автоматическом режиме. Это проверено на живых прогонах и не меняется.

Меняется другое — **видимость происходящего**. В обычной работе подозрительный шаг агента виден: он проходит через подтверждение или просто попадается на глаза в диалоге. В автоматическом режиме подтверждений нет, и шаг после блокировки выглядит как обычный успешный шаг.

Отсюда неочевидное следствие: **указание спрашивать нужно в автоматическом режиме больше, чем в любом другом**, хотя интуиция подсказывает обратное — раз режим автоматический, значит вопросов быть не должно. Вопрос здесь не про трение, а про то, что обход иначе никто не заметит.

Поэтому каждая блокировка правила заканчивается требованием спросить пользователя, а не подбирать обход, и живёт это требование в тексте самой блокировки, а не в промпте роли: промпт агент читал в начале сессии, блокировку читает в тот момент, когда упёрся. Разбор — `../principles/09-mechanical-invariants.md`, раздел «И последняя строка: спроси, а не обходи».

**И ещё одно ограничение — по способу запуска.** Вся таблица выше описывает роль, запущенную **субагентом**. Если ту же роль поднять тиммейтом в agent teams, часть полей не применяется:

| Поле | Субагент | Тиммейт в agent teams |
|---|---|---|
| `tools`, `model` | применяется | применяется |
| `permissionMode` | применяется | **нет** — тиммейт наследует режим ведущей сессии |
| `skills`, `mcpServers` | применяется | **нет** — берутся из настроек проекта |

Практическое следствие: изоляция ролей в командах держится на списке `tools` и на хуках, а не на `permissionMode`. Разбор механизмов запуска — `../docs/claude-code-mechanisms.md`.

## Конфликт memory и матрицы разрешений

Поле `memory` включает агенту persistent memory и **автоматически выдаёт ему Read, Write и Edit** — чтобы он мог вести свои файлы памяти.

Для агента, у которого Write и Edit и так есть, это ничего не меняет. Для агента, у которого их нет **намеренно**, это тихо ломает главную гарантию роли. Включив `memory: project` у `code-reviewer`, ты получаешь ревьюера, который может править код — ровно то, что вся конструкция роли исключает.

Затронуты тринадцать агентов из девятнадцати:

| Агент | Чего лишён по матрице | Что выдаёт memory |
|---|---|---|
| pm-orchestrator | Edit, Write | Edit, Write |
| code-reviewer | Edit, Write | Edit, Write |
| security-reviewer | Edit, Write | Edit, Write |
| investigator | Edit, Write | Edit, Write |
| design-reviewer | Edit, Write | Edit, Write |
| scope-challenger | Edit, Write | Edit, Write |
| finops-engineer | Edit, Write | Edit, Write |
| unit-economics-analyst | Edit, Write | Edit, Write |
| investment-analyst | Edit, Write | Edit, Write |
| vendor-auditor | Edit, Write | Edit, Write |
| browser-tester | Edit | Edit |
| devops | Write | Write |
| local-sysops | Write | Write |

**Решение:** `PreToolUse`-хук, возвращающий ролям ограничения, которые снимает поле `memory`. Реализован и лежит в [`../hooks/guard.py`](../hooks/guard.py), правило `memory`. Его матрица — исполняемая копия таблицы выше: константа `MEMORY_MATRIX` в начале файла.

Отсюда важное условие эксплуатации: у всех тринадцати перечисленных ролей `memory: project` и установленный хук — **одно целое**. Включить память, не поставив хук, значит тихо снять ограничения ролей. В шаблонах это отмечено и во frontmatter, и в теле, чтобы условие не потерялось при копировании отдельного файла.

**Не обходится через `disallowedTools`:** денилист уберёт Write/Edit целиком, и агент не сможет вести память вообще — то есть отключит ровно ту функцию, ради которой поле ставили. Нужно ограничение по путям, а не по инструментам.

## Чек-лист при добавлении нового агента

- [ ] Определён список инструментов — только необходимые
- [ ] Явно описаны инструменты, которых у агента НЕТ (и почему)
- [ ] Если агент пишет код — у него есть `Edit` и `Write`
- [ ] Если агент только проверяет — у него нет `Edit` и `Write`
- [ ] Если агент делегирует — у него есть `Agent`
- [ ] MCP-инструменты — только если реально используются в роли
- [ ] Задан `permissionMode` — `acceptEdits` только если правки агента относятся к классу D
- [ ] Задан `maxTurns` — осознанный бюджет шагов, а не «сколько не жалко»
- [ ] Задан `effort` — `high` только там, где цена ошибки выше цены прогона
- [ ] Если ставишь `memory` — проверено, что Write и Edit разрешены агенту матрицей; иначе сначала хук (см. «Конфликт memory и матрицы разрешений»)
- [ ] Проверено, что блокировка говорит агенту спросить, а не только перечисляет альтернативы — особенно если работаете в автоматическом режиме

## Чек-лист при ревизии существующего агента

- [ ] Все перечисленные инструменты реально используются агентом?
- [ ] Нет инструментов «на всякий случай»?
- [ ] Описание роли соответствует набору инструментов?
- [ ] Если агент «начал» выходить за роль — это сигнал пересмотреть инструменты или роль

## Анти-паттерны

### Слишком широкий набор инструментов

```yaml
# Плохо: ревьюер с Edit/Write
name: code-reviewer
tools: Read, Edit, Write, Bash, Agent, ...

# Хорошо: ревьюер только читает
name: code-reviewer
tools: Read, Glob, Grep, Bash
```

### Инструмент без обоснования

```yaml
# Плохо: зачем docs-writer нужен Agent?
tools: Read, Edit, Write, Agent

# Хорошо: docs-writer не делегирует другим агентам
tools: Read, Edit, Write, Glob, Grep, Bash
```

### «На всякий случай»

```yaml
# Плохо
tools: Read, Edit, Write, Bash, Agent, mcp__playwright__*, mcp__context7__*, ...

# Хорошо: только то, что реально нужно для роли
tools: Read, Edit, Write, Bash
```

## Проверка после инцидента

Если агент вышел за свою зону (сделал что-то, что не должен был):

- [ ] Какой инструмент он использовал?
- [ ] Должен ли он быть в списке инструментов агента?
- [ ] Если нет — убрать из списка
- [ ] Если да — добавить ограничение в промпт и написать eval-сценарий (см. `../principles/10-eval-suite.md`)
