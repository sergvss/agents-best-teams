# Чек-лист: декомпозиция задачи


---

## Перед декомпозицией

- [ ] Я понял задачу — могу объяснить её одним предложением
- [ ] Если задача неоднозначная — уточнил у пользователя до начала (не угадываю)
- [ ] Прочитал источники истины проекта: README + PROJECT_MAP + CHANGELOG
- [ ] Проверил git history — не было ли похожей задачи недавно

---

## Классификация по Tier

- [ ] Оцениваю: сколько файлов, сколько областей, есть ли breaking changes
- [ ] Если ≤30 строк, ≤2 файла — Tier 1 (делаю сам или 1 агент)
- [ ] Если 1 область, несколько файлов — Tier 2
- [ ] Если 2+ области или breaking change — Tier 3
- [ ] При неопределённости — беру более высокий Tier

---

## Tier 2: перед делегацией

- [ ] Определил какому агенту передать задачу (по области)
- [ ] Сформулировал ТЗ по HANDOFF-шаблону
- [ ] Указал «что прочитать перед правкой»
- [ ] Определил acceptance criteria — как убедиться, что сделано правильно
- [ ] Решил: нужен ли code-reviewer (security / RBAC / API / миграции — нужен)

---

## Tier 3: обязательный план

- [ ] Сформировал письменный план по шаблону:

```markdown
## План: <название>

**Objective:** <одно предложение: что меняется для пользователя>

**Scope:**
- IN: <что трогаем>
- OUT: <что НЕ трогаем>

**Global constraints:** <значения из ТЗ дословно, по строке: лимиты, форматы, имена — их исполнитель менять не вправе>

**Карта файлов:**
- `server/app.py` — изменить — эндпоинты режима дня
- `server/tests/test_daily.py` — создать — тесты эндпоинтов

### Задача 1: <название> → <роль>
- **Файлы:** изменить `server/db.py`, тест `server/tests/test_daily_db.py`
- **Интерфейсы:** потребляет — <сигнатура из прошлой задачи или «—»>; производит — `top_daily_scores(day: str, limit: int = 10) -> list[dict]`
- **Шаги:**
  1. Красный тест: <что проверяет>. Run: `<команда>`. Expected: падает на <проверке>
  2. Реализация. Run: `<команда>`. Expected: <N> OK
- **Зависит от:** —

### Задача 2: …

**Review Focus:** 3–5 классов входов или сбоев, которые ТЗ подразумевает, но шаги не проверяют; к каждому — тест в задаче-владельце
- <забег начат до полуночи, закончен после> → тест в задаче 2

**Risks:**
- R1: <риск + класс: R — чтение, D — правка в репозитории, W — действие с последствиями вне правки, P — привилегированное: прод, деньги, права>

**Rollback:** <как откатить; работа идёт в ветке — удаление ветки>
**Done condition:** <измеримый критерий>
**Budget:** <макс. делегаций>
```

**План — это решения, которые исполнитель не может принять сам.** Сигнатура, имя файла, ожидаемый вывод команды — решения; «TBD», «добавить валидацию», «обработать краевые случаи», «написать тесты» — нет, таких строк в плане быть не должно. План длиннее кода, который он описывает, — значит, ты написал код вместо плана.

**Задача** — наименьшая единица со своим циклом теста и своим ревью. Конфиги и документацию вливай в задачу, которой они нужны, а не отдельными задачами.

**Review Focus** закрывает то, что тесты по шагам пропускают: у obra/superpowers на замере все исполнители выпустили одно и то же падение на входе, который ТЗ подразумевало, но не называло. Планы такого формата у них требовали одного раунда правок вместо двух–четырёх.

- [ ] Дал плану свежего читателя: `scope-challenger` вторым, отдельным вызовом (или сессия без контекста этой работы) прочитал его глазами исполнителя. С первым вызовом — «надо ли делать» — не совмещал: оценка заякорилась бы на готовом плане. Вопросы разложены: ответ уже есть — в план; мелочь — решил сам и пометил; к пользователю — только меняющие результат
- [ ] Показал план пользователю — дал окно для коррекции, вопросы — одним раундом
- [ ] Если SIDE-модели настроены — получил внешний second opinion на план. Если нет — **записал в плане, что его не было**, и уверенность в оценке рисков ниже. Заменитель: свежий взгляд человека или сессии без контекста этой работы
- [ ] Только после одобрения — начал делегировать

---

## При планировании последовательности

- [ ] Определил зависимости между задачами (B нужен результат A?)
- [ ] Параллельно — только независимые области
- [ ] Последовательно: если нужно согласовать контракт между слоями — бэк первый, фронт второй

```
# Правило: если frontend нужен API-контракт backend — сначала backend
dev-backend (создать эндпоинт) → dev-frontend (написать клиент)

# Не так:
dev-backend [параллельно] dev-frontend  ← frontend не знает что подключать
```

---

## Оценка рисков

- [ ] Есть ли изменения схемы БД? → Нужна миграция + согласование
- [ ] Есть ли изменения API-контракта? → Нужно обновить документацию
- [ ] Есть ли операции класса P? → Нужно подтверждение + запись в approval log
- [ ] Есть ли внешние сервисы? → Нужны моки для тестов

---

## Признаки плохой декомпозиции

- Задача расползается по ходу работы — больше 15 шагов в Todo → переклассифицировать в Tier 3
- Агент вышел за свою зону — ТЗ было размытым
- Агент «переделал за заодно» — ТЗ не имело явных OUT ограничений
- Оркестратор не может объяснить что делает каждый агент — план был недостаточно конкретным
