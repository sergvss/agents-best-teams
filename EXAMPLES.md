# Примеры: как принципы выглядят в работе

Десять принципов из `principles/` — в виде «до и после». Каждый пример взят из ситуации, которая повторяется в реальных проектах чаще остальных.

Читать необязательно подряд: если интересует конкретный принцип, иди сразу к его разделу.

---

## 1. Команда агентов, а не суперагент

**Ситуация.** Нужно добавить эндпоинт и форму к нему.

❌ **Плохо** — один агент со всеми инструментами:

```
Агент: добавил эндпоинт, добавил форму, заодно переписал соседний
       компонент («он был некрасивый»), обновил зависимость, поправил
       линтер-конфиг, закоммитил всё одним коммитом.
```

Диагноз: у агента нет границ, поэтому нет и понятия «не моя задача». Ревьюеру приходится разбирать шесть несвязанных изменений вместо двух.

✅ **Хорошо** — роли с явными зонами:

```
dev-backend  → эндпоинт, тесты на него. Фронтенд не трогает.
dev-frontend → форма, привязка к API. Бэкенд не трогает.
code-reviewer → смотрит оба диффа, ловит расхождение контракта.
```

Почему работает: в описании каждой роли есть раздел «Что НЕ делает». Без него агент будет «помогать» в чужой зоне — и ломать то, устройства чего не знает.

## 2. Tier определяет pipeline

**Ситуация.** Поправить опечатку в тексте кнопки.

❌ **Плохо:**

```
Запрос → pm-orchestrator → dev-frontend → qa-tester → code-reviewer → devops
```

Пять делегаций, четыре передачи контекста и три отчёта ради одной строки. Стоимость выше пользы в разы, а вероятность, что кто-то по пути «улучшит» что-нибудь ещё, растёт с каждым шагом.

✅ **Хорошо:**

```
Запрос → главный агент правит сам → ответ
```

Признаки Tier 1: до 30 строк, до 2 файлов, нет изменения API-контракта, схемы БД и прав доступа. QA и ревью не нужны, если пользователь не попросил явно.

Обратная ошибка так же реальна: миграция схемы БД, пущенная как Tier 1, — это инцидент, который ждёт своего часа.

---

## 3. Подтверждение там, где оно стоит прерывания

**Ситуация.** Агент работает над задачей два часа.

❌ **Плохо** — подтверждение на каждый шаг:

```
Прочитать файл? [y/n]
Запустить тесты? [y/n]
Отредактировать файл? [y/n]
Прочитать ещё файл? [y/n]
```

К десятому вопросу человек жмёт «да» не читая. К тридцатому — жмёт «да» на `DROP TABLE`. Шум не просто бесполезен, он обучает игнорировать.

✅ **Хорошо** — по классам риска:

```
Чтение файлов, git diff, локальные тесты   → выполнять молча          [R, D]
Применение миграции, git commit            → спросить один раз        [W]
Правка .env, force-push, DDL на проде      → спрашивать каждый раз    [P]
```

Правило неопределённости: не уверен в классе — бери более строгий.

## 4. Бюджет делегаций

**Ситуация.** Оркестратор получил задачу «добавить экспорт отчётов».

❌ **Плохо:**

```
pm → dev-backend → qa → reviewer → dev-backend (правки) → qa (снова)
   → reviewer (снова) → dev-frontend (попутно нашли) → qa (в третий раз)
   → devops → ...
```

Через сорок минут человек видит результат, в котором никто уже не может сказать, что именно было сделано и почему. Ранние агенты работали с контекстом, который давно устарел.

✅ **Хорошо** — чекпоинт после N делегаций:

```
Сделано:
- dev-backend — эндпоинт GET /reports/export, 6 тестов зелёные
- qa-tester — проверил на данных стенда, нашёл кейс с пустым периодом

Осталось: форма выбора периода, запись в CHANGELOG
Заблокировано: reviewer ждёт фронтенд

Продолжать?
```

Бюджеты: Tier 1 — одна делегация, Tier 2 — четыре, Tier 3 — восемь. Чекпоинт не сбой, а точка, где человек ещё может свернуть.

## 5. Триангуляция критичных решений

**Ситуация.** Ревью диффа, затрагивающего расчёт стоимости подписки.

❌ **Плохо** — три ревьюера от одного вендора:

```
PRIMARY  = Claude
SIDE-A   = Claude (другая модель того же семейства)
SIDE-B   = Claude (третья модель того же семейства)
```

Три голоса, одна школа. Общие слепые пятна остаются общими — независимости нет, есть её видимость.

✅ **Хорошо** — три разных vendor'а:

```
PRIMARY  = Claude (Anthropic)  — знает инварианты проекта
SIDE-A   = GPT    (OpenAI)     — не знает проект, зато думает иначе
SIDE-B   = Gemini (Google)     — третья точка зрения
Правило: замечание, которое подняли двое из трёх, — блокер.
```

Vendor — это компания, обучившая модель. Gateway (через какой API ты её зовёшь) значения не имеет: OpenRouter для обеих SIDE допустим, OpenAI как vendor для обеих — нет.

## 6. Что писать в память агента

**Ситуация.** Агент закончил задачу и записывает, что узнал.

❌ **Плохо:**

```markdown
# MEMORY.md
- Проект использует FastAPI
- Эндпоинты лежат в app/routers/
- Сегодня добавил экспорт отчётов
- Функция get_user принимает user_id
```

Первые два пункта агент прочитает в коде за пять секунд. Третий устареет завтра. Четвёртый — пересказ сигнатуры, которая изменится без предупреждения.

✅ **Хорошо:**

```markdown
# MEMORY.md
- [gotcha_migrations.md] Alembic здесь настроен на две схемы;
  autogenerate по умолчанию видит только public и молча теряет вторую
- [project_billing.md] Цены хранятся в копейках целыми числами.
  Причина: были расхождения на округлении, решение осознанное
```

Правило: храни то, что дорого было узнать и глупо узнавать снова. Не храни то, что есть в коде, в `git log` или в README — дублирование создаёт противоречия.

## 7. Когда остановиться

**Ситуация.** Тест падает, агент чинит.

❌ **Плохо:**

```
Попытка 1: поправил условие — падает
Попытка 2: поправил мок — падает
Попытка 3: поправил фикстуру — падает по-другому
Попытка 4: откатил, зашёл иначе — падает
Попытка 5: добавил sleep(2) — прошло
```

Последняя строка хуже всех предыдущих: проблема не решена, а замаскирована, и всплывёт в CI через месяц.

✅ **Хорошо:**

```
Три попытки не дали результата. Останавливаюсь.

Что пробовал: условие, мок, фикстуру — падение смещается, но не уходит.
Гипотеза: тест зависит от порядка выполнения, где-то течёт глобальное
состояние между кейсами.
Что нужно от тебя: подтверди гипотезу или скажи, куда смотреть.
```

Остановка с внятным отчётом стоит дешевле, чем пятая попытка вслепую.

## 8. Журнал привилегированных действий

**Ситуация.** Через неделю выясняется, что на стенде удалены тестовые пользователи.

❌ **Плохо:**

```
— Кто это сделал?
— Кажется, агент во время задачи про очистку данных.
— Ты подтверждал?
— Вроде да. Или это было в другой сессии.
```

✅ **Хорошо** — запись в момент действия:

```
2026-08-20 14:32 | P | dev-database | DELETE FROM users WHERE is_test = true
  Задача: очистка тестовых данных на стенде
  Подтвердил: владелец проекта, явно, в этой сессии
  Затронуто: 143 строки (проверено SELECT COUNT(*) заранее)
  Бэкап: dump_20260820_1431.sql
```

Смысл журнала не в наказании, а в том, что разбор инцидента занимает минуту вместо часа.

## 9. Повторяющаяся ошибка становится кодом

**Ситуация.** Агент второй раз за месяц пытается сделать `git push --force`.

❌ **Плохо** — очередная строка в промпте:

```markdown
## Правила
- Не делай force-push
- Правда не делай
- ВАЖНО: force-push запрещён
```

Уговор действует ровно до сессии, где контекст переполнился, или до агента, который этот файл не читает.

✅ **Хорошо** — защитный хук:

```
BLOCKED [P/Privileged]: git push --force — принудительная перезапись истории.

Причина блокировки: теряются коммиты, которые уже видят другие
разработчики. Рефспек с плюсом впереди (+main) означает то же самое.

Альтернативы:
  1. git push --force-with-lease — блокируется, если кто-то запушил после тебя
  2. git push без флага — если конфликта нет
  3. git revert вместо перезаписи — история остаётся целой
```

Хук работает независимо от того, что написано в промпте, кто вызвал агента и насколько убедительно звучал запрос. Готовая реализация — в `hooks/`.

Важная деталь: блокировка без объяснения и без альтернатив учит обходить себя, а не соблюдать правило.

## 10. Проверяемая цель вместо «чтобы работало»

**Ситуация.** Задача «добавь валидацию email».

❌ **Плохо:**

```
Задача: добавь валидацию email
Готово: добавил регулярку, вроде работает
```

Ни агент, ни человек не могут сказать, сделана задача или нет. Проверка сводится к «посмотрел глазами».

✅ **Хорошо:**

```
Задача: добавь валидацию email
Критерий готовности: тесты на невалидный ввод написаны и проходят,
                     существующие тесты не сломаны

1. Написать тесты: пустая строка, без @, без домена, юникод, 300 символов
   → проверка: тесты падают (валидации ещё нет)
2. Реализовать валидацию
   → проверка: новые тесты зелёные
3. Прогнать весь набор
   → проверка: регрессий нет
```

То же правило для остальных формулировок: «почини баг» становится «напиши тест, воспроизводящий баг, потом сделай, чтобы он прошёл»; «отрефактори X» — «тесты зелёные до и после».

Сильные критерии готовности позволяют агенту работать автономно. Слабые превращают работу в череду уточнений.

## Как это связано между собой

Принципы не независимы. Типичная цепочка выглядит так:

```
Задача приходит
  → Tier определяет, кого звать (2)
  → роли работают в своих границах (1)
  → действия проходят по классам риска (3)
  → привилегированные попадают в журнал (8)
  → бюджет делегаций даёт чекпоинт (4)
  → критичное уходит на триангуляцию (5)
  → агент знает, когда остановиться (7)
  → узнанное сохраняется в память (6)
  → повторившаяся ошибка становится хуком (9)
  → всё вместе проверяется eval-сценариями (10)
```

Выпадение любого звена заметно не сразу — а через месяц, в виде инцидента, который «непонятно откуда взялся».
