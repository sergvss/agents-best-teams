# 02 — Tier-декомпозиция задач

## Зачем

Не каждая задача требует полного pipeline с QA, ревью и коммитом. Прогон 5 агентов ради правки одной CSS-переменной — это 5x overhead без выигрыша. Tier-декомпозиция решает это: **размер задачи определяет pipeline**.

---

## Три уровня

### Tier 1 — Express (мелкая правка)

**Признаки:**
- ≤30 строк кода
- ≤2 файла затронуто
- ≤5 tool calls на всю задачу
- Нет изменения API-контракта, схемы БД, прав доступа

**Примеры:** исправить опечатку в тексте, изменить цвет кнопки, переименовать переменную, добавить `console.log` для отладки.

**Pipeline:**
```
Запрос → [главный агент делает сам] → Ответ
```

QA, ревью, коммит — **не нужны** (если только пользователь не попросил явно).

**Анти-паттерн:**
```
# Не делай так для Tier 1
Запрос → pm-orchestrator → dev-frontend → qa-tester → code-reviewer → devops
# Это 3-5x overhead для 5 строк кода
```

---

### Tier 2 — Standard (средняя задача)

**Признаки:**
- 1-3 файла, одна логическая область
- Новый компонент / новый эндпоинт / новая таблица (одна)
- Изменение затрагивает только один слой (только backend ИЛИ только frontend)

**Примеры:** добавить эндпоинт с валидацией, новая форма в UI с Pinia-store, новая колонка в таблице + миграция.

**Pipeline:**
```
Запрос → pm-orchestrator
  → dev-агент (по области)
  → qa-tester (тесты + smoke)
  → [code-reviewer — если security/RBAC/API-контракт/миграции]
  → Отчёт
```

Коммит — только если пользователь явно попросил.

---

### Tier 3 — Large (мульти-областная фича)

**Признаки:**
- Затрагивает 2+ слоя (backend + frontend + БД + тесты + документация)
- Новый домен / крупный рефакторинг
- Есть breaking changes или изменение схемы прав

**Примеры:** новый модуль с API + UI + миграциями + тестами, полный рефакторинг авторизации, интеграция с внешним сервисом.

**Pipeline:**
```
Запрос → pm-orchestrator
  → [reasoning-consultant (SIDE-модель) для sanity-check плана — обязательно]
  → dev-агенты параллельно (frontend + backend + db в нужной комбинации)
  → qa-tester (тесты + регрессионный прогон)
  → code-reviewer + [SIDE-A + SIDE-B — триангуляция, см. 05-triangulated-review.md]
  → [итерация по замечаниям]
  → docs-writer (CHANGELOG + документация)
  → devops (bump версии + коммит + push — если попросили)
  → Отчёт
```

Терминология PRIMARY / SIDE-A / SIDE-B — см. глоссарий в `01-philosophy.md`. `reasoning-consultant` — это разовая консультация SIDE-модели до начала работы (не путать с триангулированным ревью после, где SIDE-модели проверяют уже готовый diff).

**Обязательно перед стартом Tier 3:**
1. Сформировать письменный план с IN/OUT scope, рисками, шагами
2. Показать план пользователю — дать окно для коррекции
3. Проконсультироваться с внешней моделью (второй взгляд на план)
4. Только потом — делегировать

---

## Матрица решений

| Условие | Tier |
|---|---|
| ≤30 строк, ≤2 файла | 1 |
| 1 область, несколько файлов | 2 |
| Затронуты security/RBAC/миграции | Минимум 2 |
| 2+ области одновременно | 3 |
| Breaking change / новый домен | 3 |
| Шагов в Todo стало >15 | Переклассифицировать в 3 |

**Правило:** если по ходу работы выясняется, что задача больше чем казалось — переклассифицируй и сообщи пользователю. Лучше остановиться и пересогласовать, чем докатить в неправильном направлении.

---

## Шаблон плана для Tier 3

```markdown
## План: <название задачи>

**Objective:** <что будет сделано — одно предложение>

**Scope:**
- IN: <что трогаем>
- OUT: <что НЕ трогаем — явно>

**Risks:**
- R1: <риск + класс R/D/W/P>
- R2: ...

**Steps:**
1. <агент> → <что делает> [parallel/sequential]
2. ...

**Validation:** <как проверим — тесты / E2E / ревью>

**Rollback:** <как откатить>

**Done condition:** <измеримый критерий готовности>

**Budget:** <макс. делегаций до чекпоинта>
```

Этот план — для человека, не для агента. Пользователь должен одобрить его до начала работы.
