# 08 — Журнал привилегированных действий

## Проблема

Через три месяца после инцидента:
- Серверные логи ротированы или недоступны
- Память о том «кто и зачем это сделал» растворилась
- `git log` показывает коммит «обновить настройки» без деталей
- Никто не помнит, что именно было изменено и как откатить

Журнал привилегированных действий решает именно это.

---

## Принцип

**Любое Privileged-действие (класс P) оставляет человекочитаемый след** с тремя элементами:
1. Что именно было сделано (не «обновили», а конкретно)
2. Почему (контекст, который пропадает быстрее всего)
3. Как откатить (если через месяц нужно будет вернуть)

---

## Где хранить

В `CHANGELOG.md` — он читается, он в git, он не ротируется.

Не в отдельном `AUDIT_LOG.md` (кто будет открывать отдельный файл?). Не в комментарии к коммиту (там нет места для контекста и отката). Именно в CHANGELOG, в отдельной секции для привилегированных действий.

---

## Формат записи

```markdown
## [v1.X.Y] — YYYY-MM-DD

### Privileged ⚠️

- **DDL prod**: добавлен индекс `idx_table_column` на `table(column)`.
  Причина: запросы выборки по `column` занимали >2с на таблице 500k строк.
  Согласовано с командой до выполнения.
  Откат: `DROP INDEX idx_table_column;`

- **Ручная корректировка данных**: пользователю id=<N> вручную выставлен флаг
  `email_verified=true` через admin-API. Причина: верификационное письмо не дошло
  по техническим причинам (provider issue), пользователь подтвердил владение
  email альтернативным способом. Тикет: #247.
```

---

## Что попадает в журнал

| Действие | Попадает в журнал |
|---|---|
| DDL на боевой БД (CREATE INDEX, ALTER TABLE, DROP) | Да |
| Ручные правки данных пользователей через admin-API | Да |
| Ручные корректировки пользовательских данных (флаги, статусы, балансы) | Да |
| Изменение конфигурации `.env` на проде | Да |
| `git push --force` | Да |
| Массовая рассылка уведомлений | Да |
| Удаление пользователя / организации | Да |
| Обычный `git push` (не force) | Нет |
| Применение штатной Alembic-миграции | Нет (есть в CHANGELOG как фича) |
| Обычный деплой | Нет |

---

## Кто пишет

- Агент, который выполнял действие, — добавляет запись в момент выполнения
- Если агент выполнил, но не написал — оркестратор или devops дописывают в том же PR/коммите

Запись создаётся **вместе с действием**, не «потом». «Потом» означает никогда.

---

## Зачем это работает

CHANGELOG читается. Это главное. Audit-логи базы данных не читаются — их смотрят только при инциденте, и тогда уже поздно восстанавливать контекст.

Когда разработчик через полгода видит странный индекс и спрашивает «а зачем это?» — ответ в CHANGELOG, с причиной и автором решения.

---

## Пример полной записи при инциденте

```markdown
### Privileged ⚠️

- **Incident response — DDL prod 2024-11-08 03:42 UTC**:
  В таблице `sessions` удалены 15 000 «зависших» записей старше 90 дней.
  ```sql
  DELETE FROM sessions WHERE created_at < NOW() - INTERVAL '90 days'
    AND status = 'pending';
  ```
  Причина: таблица разрослась до 2M строк, auth-запросы деградировали до 8с.
  Выполнено вручную с подтверждения владельца проекта в 03:38 UTC.
  Откат: невозможен (данные удалены), но записи не влияли на активных пользователей
  (статус `pending` + возраст >90 дней = брошенные сессии).
  Мониторинг после: auth p95 вернулся к <200ms в течение 5 минут.
```
