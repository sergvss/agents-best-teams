# 06 — Гигиена persistent memory

## Зачем агентам память

Каждая сессия PRIMARY-агента (в любой платформе — Claude Code / Cursor / Codex / Cline / ...) начинается с чистого контекста. Без persistent memory агент каждый раз «с нуля» выясняет, почему вот этот инвариант существует, какой порт использует dev-сервер, и что в прошлый раз сломалось при попытке сделать X.

Persistent memory — это **институциональное знание агента** между сессиями. То, что дорого было узнать и что глупо узнавать снова.

---

## Структура хранения

Рекомендуемая схема:

```
<memory_dir>/
  <agent-name>/
    MEMORY.md          # индекс — ссылки на файлы + однострочные описания
    gotcha_*.md        # конкретные ловушки и неочевидности
    reference_*.md     # ссылки на важные части кода / документации
    project_*.md       # решения, паттерны, конвенции проекта
```

`<memory_dir>` определяется платформой (для Claude Code — `.claude/agent-memory/`, для Cursor — `.cursor/agent-memory/`, и т.д. — задаётся в `agents.config`, секция `[primary].memory_dir`).

`MEMORY.md` подгружается автоматически в каждую сессию агента. Остальные файлы — по ссылкам из него.

### В Claude Code это делается одним полем

Схема выше изначально описывалась как ручная конвенция. В Claude Code она стала нативной: поле `memory` во frontmatter субагента.

| Значение | Куда пишет | Когда брать |
|---|---|---|
| `project` ←★ | `.claude/agent-memory/<agent>/` | Знание о проекте, едет в git вместе с командой |
| `user` | `~/.claude/agent-memory/<agent>/` | Знание про все проекты машины |
| `local` | `.claude/agent-memory-local/<agent>/` | Проектное, но не в git |

Платформа сама подставляет агенту инструкции по ведению памяти и подгружает первые 200 строк (или 25 КБ) его `MEMORY.md`. Структура совпадает с описанной выше — надстройка из `gotcha_*.md` / `reference_*.md` / `project_*.md` поверх неё продолжает работать, платформа имена вспомогательных файлов не диктует.

**Два условия, без которых поле не сработает как задумано:**

1. Память входит в auto memory. Если она выключена в settings или через `CLAUDE_CODE_DISABLE_AUTO_MEMORY`, поле молча не действует.
2. `memory` автоматически выдаёт агенту Read, Write и Edit. Для агента, лишённого Write/Edit намеренно, это ломает гарантию роли — нужен хук ограничения путей. Разбор и список затронутых ролей — `../checklists/permission-checklist.md`, раздел «Конфликт memory и матрицы разрешений».

Для других платформ остаётся ручная схема из начала раздела. Что именно писать в память — вопрос ниже, и он от платформы не зависит.

## Что хранить

### Хранить стоит

- **Gotchas** — «если сделаешь X — сломается Y, потому что Z». Особенно если это неочевидно из кода.
- **Архитектурные решения** — почему было выбрано именно это, а не очевидный альтернативный вариант.
- **Инварианты**, которые нигде не задокументированы явно.
- **Паттерны ошибок** — типичные нарушения, которые повторялись в разных задачах.
- **Конвенции** — соглашения, которые сложились практикой и не прописаны в правилах проекта (`CLAUDE.md` / `.cursor/rules` / эквивалент).

### Не хранить

- То, что есть в коде — агент может прочитать код.
- То, что есть в `git log` — `git blame` авторитетнее памяти.
- То, что есть в README / PROJECT_MAP — дублирование создаёт противоречия.
- Текущее состояние задачи — это для Todo/Plan, не для постоянной памяти.
- JWT-токены, пароли, учётные данные — никогда, ни при каких условиях.

## Правила гигиены

### Один файл — одна тема

```
# Плохо: всё в одном MEMORY.md
## Gotcha: dev-server port
## Convention: API response error format
## Reference: cache TTL policy
## Gotcha: migrations idempotency
[... 300 строк ...]

# Хорошо: отдельные файлы
MEMORY.md (индекс, 20 строк)
gotcha_ports.md
gotcha_migrations.md
reference_cache_policy.md
```

### Лимит 200 строк на файл

Файл больше 200 строк — сигнал для кьюрирования. Убрать устаревшее, объединить похожее, оставить только высокоценное.

### DEPRECATED-метка перед удалением

```markdown
# DEPRECATED 2024-09-15 — заменено на reference_cache_policy_v2.md
...старое содержимое...
```

Метка даёт «окно» понять что устарело, а что просто забыто. Через один спринт — удалить.

### Триггер на кьюрирование

Не нужно кьюрировать после каждой задачи. Триггеры:
- После крупной сессии (Tier 3 / релиз)
- Когда файл превысил 200 строк
- Когда замечаешь, что читаешь память и треть — уже не актуальна

---

## Что НЕ делать с памятью

- **Не писать туда то, что может прочитать сам** — код в репозитории авторитетнее.
- **Не дублировать** общую документацию — memory это личный конспект, не вторая копия README.
- **Не накапливать список задач** — это Plan/Todo, не long-term memory.
- **Не хранить credentials** — никакие, ни в каком формате.

---

## Пример хорошей записи в memory

```markdown
# gotcha_timezone_in_tests.md

## Тесты падают на CI из-за UTC vs локального времени

**Почему:** на CI runner timezone установлен в UTC, локально — в зоне разработчика.
Тесты, сравнивающие `datetime.now()` с фикстурами, проходят локально и падают на CI.

**Как применять:** в тестах с датами — всегда работать через UTC явно:
`datetime.now(timezone.utc)`, не `datetime.now()`. Фикстуры тоже в UTC.

**Симптом нарушения:** тест проходит локально, падает в CI с разницей в несколько часов
в assertion на timestamp.
```
