# 04 — Бюджеты оркестрации

## Проблема каскадной делегации

Без ограничений оркестратор будет делегировать бесконечно:

```
pm-orchestrator → dev-backend → qa-tester → code-reviewer
  → dev-backend (правки) → qa-tester (повторно) → code-reviewer (повторно)
    → dev-frontend (попутно нашли) → qa-tester (снова) → devops → ...
```

К моменту, когда пользователь видит результат, оркестратор потерял нить, агенты работали с устаревшим контекстом, и никто не знает, что именно было сделано.

**Бюджет делегаций** — это принудительный чекпоинт: после N шагов оркестратор останавливается и докладывает человеку.

---

## Бюджеты по Tier

| Tier | Макс. делегаций до чекпоинта | Что делать при превышении |
|---|---|---|
| Tier 1 | 1 | Если расползается — переклассифицировать в Tier 2, сообщить пользователю |
| Tier 2 | 4 | Промежуточный отчёт: что сделано, что осталось — потом продолжать |
| Tier 3 | 8 | Обязательный чекпоинт: статус + риски оставшихся шагов + спросить продолжать ли |

---

## Формат чекпоинта

```
Сделано:
- dev-backend — добавил эндпоинт GET/POST /items/ (согласно API-контракту проекта)
- qa-tester — написал 8 тестов, все прошли

Осталось:
- dev-frontend — форма создания Item
- docs-writer — CHANGELOG + README

Заблокировано:
- code-reviewer ждёт пока dev-frontend закончит

Стоимость на текущий момент: ~$0.03 (если использовался внешний LLM)

Продолжать? [по умолчанию да, остановись если "нет" или нужны уточнения]
```

Чекпоинт — не сбой. Это точка контроля, где человек может сказать «стоп, пойдём в другую сторону» до того, как накопится технический долг.

## Бюджет на платные API

Когда в pipeline участвуют SIDE-модели (внешние LLM-ревьюеры) — добавляй cost-контроль. Терминология PRIMARY / SIDE — см. глоссарий в `01-philosophy.md`.

### Базовые пороги

| Ожидаемые расходы на операцию | Действие |
|---|---|
| ≤ `per_review_usd` (по умолчанию $0.50) | Выполнять без подтверждения |
| > `per_review_usd` | Оценить заранее, спросить пользователя |
| Близко к `monthly_usd` (>80%) | Предупредить, дальше — спрашивать |
| Превысили `monthly_usd` | Стоп, эскалация владельцу |
| Бесконечный цикл / автомат | Всегда спрашивать |

### Порядок проверки лимитов

Перед **каждым** SIDE-вызовом агент должен проверять лимиты в следующем порядке (от широкого к узкому):

1. **`monthly_usd`** (hard limit) — если ledger показывает превышение → стоп, независимо от других порогов. На `monthly_usd` нельзя ставить `on_overflow = "warn"`.
2. **`per_tier3_usd`** (на всю текущую Tier-3 операцию) — суммарная стоимость всех SIDE-вызовов в рамках одного `Запрос → ... → Отчёт`. Если несколько раундов ревью подряд незаметно нарастили cost — это поймается здесь.
3. **`per_review_usd`** (на конкретный прогон) — стоимость одного triangulation-цикла (PRIMARY + SIDE-A + SIDE-B).

Любой превышенный hard-limit — стоп до явного подтверждения пользователя. `on_overflow = "ask_user"` означает «спросить и продолжить с согласия»; `"block"` — «остановить безусловно». Stateful ledger (накопительная стоимость за Tier-3 операцию и за месяц) — обязательная часть реализации, не опциональная.

### Структура `[budget]` в `agents.config`

Конфигурация лимитов живёт в проекте, не в принципах. Пример (см. полный шаблон в `agents.config.example` в корне репо):

```toml
[budget]
per_review_usd = 0.50         # лимит на одно ревью diff'а
per_tier3_usd  = 2.00         # лимит на полный Tier-3 цикл (план + триангуляция)
monthly_usd    = 50.00        # общий месячный лимит на SIDE-вызовы
on_overflow    = "ask_user"   # ask_user | block | warn
```

Агент перед вызовом SIDE-модели:
1. Считает оценочную стоимость операции (по токенам входа + ожидаемым токенам выхода × прайс модели)
2. Сверяет с лимитами → решает: выполнить / спросить / заблокировать
3. После операции — обновляет ledger (накопительная стоимость за месяц)

### Ориентиры стоимости (порядок величины, **не** актуальный прайс)

- Консультация с SIDE-моделью (короткий вопрос): ~$0.001–$0.01
- Ревью небольшого diff (≤200 строк) одной SIDE-моделью: ~$0.01–$0.05
- Ревью крупного diff (~1500 строк) двумя SIDE-моделями: ~$0.10–$0.20

Разброс цен между моделями, которые проходят порог ревью, доходит до 13 раз — и он почти не связан с их местом в рейтинге (см. следующий раздел). Поэтому «взять SIDE подешевле» работает ровно до тех пор, пока обе модели остаются **выше порога**. Ниже порога экономия покупается за счёт единственной функции ревью; там, где бюджет жмёт, правильная ручка — уровень `effort`, а не модель попроще.

Если планируешь несколько раундов ревью или большой diff — оцени суммарную стоимость **до** запуска и сравни с `per_tier3_usd`.

## Выбор модели для ревью: порог, а не тир

Цель ревью — поймать дорогую ошибку до прода. Поэтому **на самом ревью экономить — false economy**: если SIDE-модель не углубилась и пропустила блокер, ты заплатил $0.05 за «approve» и $X за прод-инцидент. С другой стороны, **самый дорогой флагман на каждый PR** — тоже false economy в обратную сторону: классификация и обзорная проверка не требуют топовой модели.

Решение — **измеримый порог** и две независимые ручки: выбор модели и уровень effort.

### Почему порог, а не класс модели

Раньше здесь стояла таблица из четырёх классов (top / strong / mid / light) с примерами моделей в каждом. Эта схема сломалась, и вот на чём.

На август 2026 модель Google со словом `flash` в имени даёт coding_index 76.1, обходя вчерашний флагман OpenAI (74.9) и стоя при этом в 13 раз дешевле. Слова `mini`, `flash`, `lite`, `pro` в слаге больше не сообщают об уровне модели ничего достоверного — они означают позиционирование внутри линейки вендора, а линейки несопоставимы между собой.

Поэтому классификация по названию заменена на порог по измеримой величине.

### Два режима вместо четырёх классов

Порог берётся по **coding_index** (Artificial Analysis; публикуется в каталоге OpenRouter, сортировка `coding-high-to-low`).

| Режим | Порог | Когда | Цена прогона (×2 SIDE) |
|---|---|---|---|
| **Ревью** ←★ | coding_index ≥ **74** | Дефолт для триангуляции на Tier-2 / Tier-3 | $0.10–$0.20 |
| **Высокий риск** | coding_index ≥ **77** + effort `high` | Биллинг, прод-RBAC, DDL прода, миграция горячих данных | $0.25–$0.60 |

Цена посчитана для diff'а порядка 30k токенов входа и 4k выхода на каждого ревьюера, по ценам каталога на август 2026. Свой diff считай по своим — цифры здесь для порядка величины, не для планирования бюджета.

Ниже 74 **на ревью** не опускаться ни в каком режиме — обоснование ниже. На задачи, которые ревью не являются (классификация, роутинг, dispatch), порог не распространяется.

Конкретные слаги моделей намеренно **не перечисляются в этом файле**: они живут в одном месте, в `agents.config` проекта (пример — `agents.config.example` в корне репо). Так протухает одна точка, а не две.

### Вторая ручка: effort

Уровень рассуждений (`low` / `medium` / `high` / `xhigh` / `max`) — независимый от модели регулятор стоимости. Одна и та же модель на `medium` и на `xhigh` различается по цене прогона в разы.

Практическое следствие: **экономить нужно через effort, а не через модель ниже порога**. Модель ниже порога не углубится в diff в принципе, сколько ей ни дай effort. Модель выше порога на `medium` — всё ещё осмысленный ревьюер.

Раз в квартал переоценивай `agents.config` под актуальный каталог. Каталог устаревает, правило порога — нет.

### Рекомендуемые SIDE-пары по типу прогона

| Тип прогона | SIDE-A | SIDE-B |
|---|---|---|
| Tier 1 — sanity / классификация | порог не нужен, это не ревью | — |
| Tier 2 — обычный diff | ≥74, effort `medium` | — (не запускается) |
| Tier 2 — security / RBAC / API-контракт / миграции | ≥74, effort `high` | ≥74, effort `high` |
| **Tier 3 — крупная фича** ←★ | **≥74, effort `high`** | **≥74, effort `high`** |
| Tier 3 — затрагивает биллинг / прод-RBAC / DDL прода | ≥77, effort `high` | ≥74, effort `high` |
| Финальная приёмка перед прод-релизом высокого риска | ≥77, effort `xhigh` | ≥77, effort `high` |

### Откуда взялся порог 74

Эмпирика с триангуляции самой этой методологии при её разработке:

- **Модели выше порога:** verdicts `changes_requested` с 3–7 конкретными блокерами уровня концепции (vendor vs gateway, дыра в логике бюджета, путаница ролей).
- **Модели ниже порога:** один verdict `approve` за 251 токен выхода. Модель не углубилась в diff вообще. Прогон стоил копейки, но **полезности не дал**.

Тогда провалившиеся модели назывались `mini` и `flash-lite`, и вывод был сформулирован как «не берите mid-tier». Это была неверная генерализация: дело было не в суффиксе в имени, а в том, что обе оказались ниже порога способности читать diff целиком. Сегодня модель с тем же суффиксом `flash` этот порог проходит — и работает как полноценный ревьюер.

Правильная формулировка: **есть уровень, ниже которого ревью вырождается в ритуал**. Он измеряется, а не угадывается по названию.

Задачи ниже порога у моделей тоже есть — классификация, роутинг, dispatch. Просто это не code review.

### Антипаттерны

- ❌ **«Возьмём самое дешёвое ради экономии»** — если модель ниже порога, ревью станет ритуалом и блокеры начнут уходить в прод. Экономия покупается за счёт единственной функции этого ревью.
- ❌ **«Возьмём два флагмана на каждый PR»** — для 99% PR не нужно. Деньги быстрее всего сгорают на Tier-1 правках.
- ❌ **«Выберем модель по названию тира»** — `pro` в слаге не гарантирует уровень, `flash` не означает слабость. Смотри индекс.
- ✅ **Правильно:** порог по индексу как жёсткое условие, effort как регулятор цены внутри порога.

## Кэширование промптов — рычаг сильнее выбора модели

Бюджеты выше отвечают на вопрос «сколько тратить». Кэширование отвечает на вопрос «за что не платить дважды», и по величине эффекта обычно перевешивает выбор модели.

### Арифметика

У всех крупных провайдеров цена делится на три части: обычный ввод, запись в кэш и чтение из кэша.

| | Доля от цены обычного ввода |
|---|---|
| Чтение из кэша | **≈ ×0.1** — устойчиво у всех крупных провайдеров |
| Запись в кэш | зависит от провайдера: от надбавки около ×1.25 до отдельной платы за хранение |

Чтение — та часть, ради которой всё и делается, и она предсказуема. Цена записи различается: одни провайдеры берут надбавку к обычному вводу, другие тарифицируют хранение кэша отдельно и заметно дешевле. Смотри поля `input_cache_read` и `input_cache_write` в каталоге для **своих** моделей, а не бери цифры отсюда.

Точка окупаемости при надбавке ×1.25 — **второе обращение** к тому же префиксу: один запрос даёт переплату на четверть, пять запросов — экономию около 60%, двадцать — около 75%. Там, где запись дешевле, кэш окупается сразу.

Для команды агентов это означает, что львиная доля расходов приходится не на модель, а на то, сколько раз одинаковый контекст пересылается заново.

### Что даёт попадание в кэш

Кэш работает по **общему префиксу**. Совпадать должно начало запроса, целиком и побайтово.

Отсюда единственное практическое правило: **стабильное — в начало, изменчивое — в конец**.

```
[системный промпт роли]      ← не меняется между задачами
[инварианты проекта]         ← меняются раз в месяц
[материалы задачи]           ← меняются каждый раз
[сам запрос]                 ← меняется каждый раз
```

### Что кэш убивает

- **Метка времени или счётчик в начале промпта.** Одна изменившаяся строка вверху обесценивает весь кэш ниже. Это самый частый способ случайно платить полную цену.
- **Перегенерация описаний ролей на каждый запуск.** Шаблон агента должен быть файлом, а не строкой, которую собирает код.
- **Перетасовка порядка блоков.** Тот же набор материалов в другом порядке — это другой префикс.
- **Холодный старт вместо продолжения.** Пять коротких сессий по одной задаче дороже одной длинной: каждая платит за запись кэша заново.

### Где это заметнее всего

**Триангуляция.** SIDE-модель получает один и тот же контекст проекта при каждом ревью. Без кэша ты платишь за него полную цену на каждом прогоне; с кэшем — один раз, дальше по десятой части.

**Циклы правок.** Ревью → правка → повторное ревью на том же диффе: второй и третий проход почти бесплатны по вводу, если префикс не поехал.

Учитывай срок жизни кэша: по умолчанию он измеряется минутами, у части провайдеров есть вариант на час дороже по записи. Если между прогонами проходит больше — префикс придётся записывать заново, и экономия не наступит.

## Параллельно vs последовательно

**Параллельно** (несколько агентов в одном шаге) — когда области независимы:

```
# Хорошо: backend и frontend независимы, если контракт API уже согласован
→ dev-backend [параллельно] dev-frontend
```

**Последовательно** — когда B нужен результат A:

```
# Правильно: миграция сначала, тесты после
→ dev-backend (создать модель + миграцию)
→ qa-tester (написать тесты с новым полем)
```

**Золотое правило для QA → review → devops:** эта цепочка всегда последовательная. Нет смысла ревьюить код, который ещё тестируется.

## Анти-паттерн: оркестратор-рекурсия

```
# Плохо: pm-orchestrator спавнит другой pm-orchestrator
pm-orchestrator (задача А)
  → pm-orchestrator (подзадача B)  ← потеря контекста, двойной overhead
    → pm-orchestrator (подзадача C)  ← полная каша
```

Если оркестратор работает и понимает что задача больше — **не спавнит вложенного оркестратора**. Делает чекпоинт пользователю и договаривается о продолжении.
