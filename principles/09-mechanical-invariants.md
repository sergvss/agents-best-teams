# 09 — Механические инварианты и защитные hooks

## Принцип

Если одна и та же ошибка повторяется во второй раз — это не проблема промпта. Это проблема архитектуры.

Уговоры в промпте («пожалуйста, не делай X») работают в лучшем случае в рамках одной сессии. Hooks — работают всегда, независимо от того, что написано в промпте, кто вызвал агента, и насколько убедительным был запрос пользователя.

**Правило:** повторяющиеся нарушения → code, not prompt.

---

## Что такое защитный hook

Hook — это скрипт, который перехватывает вызов инструмента агентом **до** его выполнения. Агент намеревается выполнить команду → hook проверяет → разрешает или блокирует с объяснением.

В Claude Code это событие `PreToolUse`. В других платформах — middleware, обёртки над tool-calls или pre-execution callbacks.

### Контракт

Хук получает JSON на stdin и отвечает решением. Заблокировать можно двумя способами.

**Через JSON** — рекомендуемый, потому что позволяет объяснить причину:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "BLOCKED [P/Privileged]: ..."
  }
}
```

Код возврата при этом `0`: решение передаётся содержимым, а не кодом.

**Через код возврата** — `exit 2` блокирует вызов, `stderr` уходит агенту как объяснение. Короче, но причина не структурирована. Кроме `deny`, у `permissionDecision` есть `allow`, `ask` и `defer`. `ask` — не отказ, а окно подтверждения для человека; разбор ниже, в разделе «Отказ или подтверждение».

Что приходит на вход:

| Поле | Содержимое |
|---|---|
| `tool_name` | Имя инструмента: `Bash`, `Edit`, `Write`, ... |
| `tool_input` | Аргументы вызова: `.command` у Bash, `.file_path` у Edit и Write |
| `agent_type` | Имя субагента, если вызов произошёл внутри него. В главном потоке поля нет |
| `cwd`, `session_id`, `permission_mode` | Контекст вызова |

Наличие `agent_type` — то, что делает возможными ролевые правила: один хук может знать, какая именно роль сейчас работает, и применять к ней её ограничения.

### Событий больше, чем одно

`PreToolUse` — главное, но не единственное. Полезные для команды агентов:

| Событие | Зачем |
|---|---|
| `PreToolUse` | Заблокировать опасное до выполнения — основной инструмент |
| `PostToolUse` | Реакция после: форматирование, линт, запись в approval log (принцип 08) |
| `SubagentStart` / `SubagentStop` | Границы работы роли: подготовка контекста и разбор результата |
| `Stop` | Не дать завершить задачу, пока не выполнено условие готовности (принцип 07) |
| `PreCompact` | Сохранить важное до сжатия контекста (принцип 06) |
| `PermissionDenied` | Узнать об отказе классификатора auto mode и разрешить модели повтор. Срабатывает только на него — не на отказ хука и не на отказ человека в окне — и текста модели не передаёт |
| `TeammateIdle` | Не дать роли уйти в простой, пока её часть не доведена |
| `TaskCreated` / `TaskCompleted` | Ворота на постановку и на закрытие задачи в общем списке команды |

Последние три относятся к работе нескольких параллельных сессий и позволяют перенести условие готовности с одной роли на всю команду.

### Хук не обязан быть скриптом

Кроме типа `command` есть `http` (решение принимает внешний сервис), `mcp_tool`, а также `prompt` и `agent` — эти два передают решение модели.

Тип `agent` означает, что судьёй на месте хука работает LLM. Так выражаются проверки, которые не описать регуляркой. Плата — деньги и задержка на каждом вызове. Для механических инвариантов бери `command`: они на то и механические, что решаются кодом.

## Минимальный набор блокировок

Рекомендуемый минимум для любого production-проекта. `BLOCKED` — отказ, `CONFIRM` — окно подтверждения: вызов выполнится только после «да» человека.

```
Деструктив файловой системы:
  rm -rf /      → BLOCKED [P/Privileged]
  rm -rf .      → BLOCKED [P/Privileged]

Git деструктив:
  git push --force       → CONFIRM [P/Privileged]
  git push origin +ветка → CONFIRM [P/Privileged]  (тот же force, другой синтаксис)
  git push --mirror      → CONFIRM [P/Privileged]
  git push --delete      → CONFIRM [P/Privileged]  (удаление ветки на сервере)
  git reset --hard       → CONFIRM [W/Write]
  git clean (без -n)     → CONFIRM [W/Write]
  git checkout -- .      → CONFIRM [W/Write]
  git restore .          → CONFIRM [W/Write]  (современная форма того же отката)

SQL деструктив:
  DELETE FROM <table>  (без WHERE)  → BLOCKED [P/Privileged]
  UPDATE <table>       (без WHERE)  → BLOCKED [P/Privileged]
  DROP любого объекта  → CONFIRM [P/Privileged]
  TRUNCATE             → CONFIRM [P/Privileged]

Защита конфигурации:
  Edit/Write на .env*  → BLOCKED [P/Privileged]
  echo ... > .env      → BLOCKED [P/Privileged]  (та же запись, мимо редактора)
  sed -i / rm / mv на .env* → BLOCKED [P/Privileged]

Возврат ролевых ограничений:
  Write/Edit роли вне её зоны  → BLOCKED [W/Write]
```

Последний пункт нужен потому, что поле `memory` выдаёт субагенту Read, Write и Edit в обход списка `tools` — и тем самым снимает ограничения роли, которую матрица разрешений намеренно этих инструментов лишила. Промптом это не чинится: инструмент физически есть. Разбор — `../checklists/permission-checklist.md`.

## Готовая реализация

Всё перечисленное выше реализовано и лежит в [`../hooks/`](../hooks/): несколько скриптов на Python без внешних зависимостей, конфигурация для подключения и тесты, половина которых проверяет **отсутствие** ложных срабатываний.

```bash
# Все .py разом: конфигурация ссылается на пять хуков, и каждому нужен
# messages.py — без него guard.py отказывает на любой команде.
cp hooks/*.py <проект>/.claude/hooks/
cp hooks/settings.example.json <проект>/.claude/settings.json
```

Точное число тестов здесь не называется намеренно: оно меняется каждый выпуск, а число, названное однажды, начинает врать молча.

Подробности, настройка правил и честный список того, чего эти хуки **не** делают — в [`../hooks/README.md`](../hooks/README.md).

Это единственная часть методологии, привязанная к конкретной платформе. Принцип от неё не зависит: перехват перед выполнением есть в любом harness, а формат сообщения о блокировке переносится дословно.

## Формат сообщения блокировки

Критически важно: hook не просто блокирует — он **объясняет и предлагает альтернативу**.

```
BLOCKED [P/Privileged]: DELETE FROM без WHERE — удаление всех строк таблицы.

Причина блокировки: запрос без WHERE почти всегда означает опечатку или
недодуманное условие. Откатить его нечем.

Альтернативы:
  1. Добавь WHERE с явным условием
  2. Сначала оцени объём: SELECT COUNT(*) с тем же WHERE
  3. Если нужно очистить таблицу целиком — сделай дамп и выполни команду сам
```

Анти-паттерн: блокировка без объяснения и без альтернатив:

```
# Плохо
Command blocked.

# Тоже плохо — альтернатива сама заблокирована
BLOCKED: rm -rf .
Alternative: rm -rf * (тоже заблокирована)
```

### И последняя строка: спроси, а не обходи

Список альтернатив закрывает ожидаемые случаи. Неожиданный он не закрывает — и тогда агент, оставленный без указания, начинает **подбирать обход**: это выглядит инициативой и ощущается как решение задачи.

Поэтому каждая блокировка правила заканчивается одинаково:

```
Ни одна альтернатива не подходит — спроси пользователя, а не подбирай обход.
В автоматическом режиме это важнее всего: там за каждым шагом никто
не смотрит, и найденный обход останется незамеченным.
```

Три вещи здесь неочевидны и стоят того, чтобы их назвать.

**Место выбрано намеренно.** Указание живёт в тексте блокировки, а не в промпте роли. Промпт агент читал в начале сессии, за десятки шагов до этого момента; текст блокировки он читает ровно тогда, когда упёрся. Наблюдение подтверждено дважды: агенты пользовались альтернативой **из текста самой блокировки**, а не той, что была записана в их роли.

**Дописывается в одной точке.** Все сообщения правил проходят через общую функцию отказа, и хвост добавляется там — а не копируется в семнадцать текстов, где семнадцатый однажды забудут. Проверяется тестом.

**Ошибкам конфигурации этот хвост не нужен.** Опечатку в списке правил чинит человек в файле, а не агент вопросом. Смешивать «не знаю, как поступить с задачей» и «настройка сломана» — значит обесценивать оба сообщения.

Отдельно про автоматический режим. Обычно за агентом смотрят: подозрительный шаг видно в диалоге. В автоматическом режиме подтверждения не запрашиваются, и **обход перестаёт быть заметным** — он выглядит как обычный успешный шаг. Именно поэтому указание спрашивать нужно там больше, чем где-либо, хотя интуиция подсказывает обратное: раз режим автоматический, значит вопросов быть не должно.

## Отказ или подтверждение

Отказ хука ничем не снимается. Для `rm -rf /` это правильно. Для force-push уже нет: у него есть законные случаи, и агент, упёршись в отказ, мог только сказать «выполните сами». Человек переключался в терминал и набирал команду руками — а хук, который приходится обходить руками, со временем отключают.

У `PreToolUse`-хука есть второй исход — `permissionDecision: "ask"`. Вызов не выполняется, пока человек не нажмёт «да» в окне подтверждения Claude Code. Окно появляется и в auto mode: классификатор может такой вызов отклонить, но одобрить молча не может. Подделать нажатие агент не может — в отличие от фразы «пользователь разрешил» в тексте задачи. Там, где окно показать некому, — в неинтерактивном запуске, в том числе с `bypassPermissions`, — оно становится отказом, а не молчаливым согласием: проверено прогоном.

| Исход | Правила | Почему |
|---|---|---|
| **Отказ** | `rm -rf` по корню, `~`, `.`, маске и переменной; `DELETE` и `UPDATE` без `WHERE`; запись в `.env`; запись роли вне её зоны | Законного случая нет, или окно отменило бы смысл правила: «пусть ревьюер правит код?» — это отмена матрицы ролей |
| **Окно подтверждения** | force-push и его формы, `--mirror`, удаление ветки на сервере, `reset --hard`, `clean`, `checkout -- .` и `restore .`; `DROP` любого объекта, `ALTER TABLE … DROP`, `TRUNCATE` | Законные случаи есть, и решение за человеком, а не за хуком |

Четыре вещи здесь неочевидны.

**Отказ сильнее окна, и порядок в команде не важен.** В `git push --force && rm -rf /` первое правило, открой оно окно сразу, пропустило бы после «да» и вторую команду — непроверенной. Поэтому хук разбирает команду целиком: отказ завершает разбор немедленно, а окно открывается в самом конце и только если отказа не было.

**У окна два адресата и два текста.** Причину в окне Claude Code показывает только человеку, агенту — нет. Человеку уходит, что он подтверждает и чем это опасно. Агенту отдельно, рядом с результатом, — альтернативы и что делать, если вызов не прошёл: не повторять действие в другой форме, предложить альтернативу или спросить. Этот текст приходит, когда человек разрешил, и когда окно показать некому — там вызов становится отказом. **Если человек нажал «нет», вложение не доставляется**, это проверено в живой сессии: агент получает сообщение самого Claude Code — остановиться и ждать указаний. Главное, не искать обход, закрывает платформа. Альтернативы в этот момент агенту не видны, но человек, только что отказавший, рядом.

**В окне не пишется «заблокировано».** Если человек согласится, блокировки не будет, и `BLOCKED` в окне было бы неправдой. Заголовок — `CONFIRM`.

**Окно обесценивается частотой.** Каждое лишнее окно учит нажимать «да», не читая. Поэтому окном отвечают только операции с законными случаями, а запрос без `WHERE` остался отказом: это почти всегда ошибка, и подтверждать её окном значит тренировать рефлекс.

## Отказ классификатора auto mode

Хук — не единственный источник отказов. В auto mode действия проверяет классификатор Claude Code, и в реальных сессиях его отказы встречаются заметно чаще, чем блокировки хука. Текст такого отказа велит модели остановиться и объяснить пользователю, что она пыталась сделать, — и агент заканчивает словами «выполните сами».

По транскриптам вышло иначе: если агент спросил через меню вопросов и получил «да», повтор того же действия проходил, и повторных отказов не было. Документация Claude Code этого не обещает — ответ из меню приходит результатом инструмента, — так что это проверенная практика, а не контракт. Документированный ручной путь — `/permissions`, вкладка Recently denied, клавиша `r`.

Хук `denial_guidance.py` превращает находку в поведение:

- **главный диалог** на старте сессии, в том числе после сжатия контекста, получает правило: после отказа классификатора спросить через `AskUserQuestion` — что за действие, зачем, чем рискуем — и при согласии повторить один раз. Отказ хука согласием не снимается, и спрашивать о нём не нужно;
- **каждый субагент** получает своё правило. `AskUserQuestion` у субагентов нет вовсе, поэтому роль после отказа не ищет обход и не советует пользователю, а заканчивает отчёт блоком `НУЖНО РАЗРЕШЕНИЕ`: точное действие, зачем, риск. Главный диалог узнаёт блок по маркеру, спрашивает человека и выполняет одобренное сам.

`PermissionDenied` для этого не годится, хотя по названию подходит: он срабатывает только на отказ классификатора, текста модели не передаёт и умеет лишь сказать «можно повторить». Без согласия человека это приглашение уговаривать классификатор.

## Самопротиворечивость

Проверь: предложенные альтернативы в сообщении блокировки не должны сами быть заблокированы тем же hook'ом. Это классическая ловушка: пользователь видит альтернативу, пробует — снова блокировка.

---

## Что hook НЕ делает

- Не блокирует всё подряд (синдром «безопасного» но бесполезного hook'а)
- Не заменяет промпт — он дополняет, закрывая классы ошибок, которые промпт не покрывает надёжно
- Не принимает архитектурные решения — только техническая защита

---

## Принцип минимальной инвазивности

Хороший hook срабатывает редко — только на реальные нарушения. Если hook блокирует рутинные операции, разработчики начнут его отключать. Настраивай паттерны точно.

```
# Плохо — слишком широко, заблокирует обычные операции
rm .*   →  блокировать

# Хорошо — точечно
rm -rf /        →  блокировать
rm -rf .        →  блокировать
rm -rf [путь]   →  не блокировать (это нормальная операция)
```

---

## Когда hook не помогает

Hooks — защита от нечаянных ошибок, не от целенаправленного обхода. Если пользователь сознательно хочет выполнить операцию под отказом — например, действительно очистить таблицу целиком, — он выполняет её вручную. Это правильно: осознанное действие плюс ручное выполнение трудно совершить случайно. Для операций с законными случаями, вроде force-push, ту же роль играет окно подтверждения: решение остаётся за человеком, но переключаться в терминал не нужно.
