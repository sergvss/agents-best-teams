# 09 — Механические инварианты и защитные hooks

## Принцип

Если одна и та же ошибка повторяется во второй раз — это не проблема промпта. Это проблема архитектуры.

Уговоры в промпте («пожалуйста, не делай X») работают в лучшем случае в рамках одной сессии. Hooks — работают всегда, независимо от того, что написано в промпте, кто вызвал агента, и насколько убедительным был запрос пользователя.

**Правило:** повторяющиеся нарушения → code, not prompt.

---

## Что такое защитный hook

Hook — это скрипт, который перехватывает вызов инструмента агентом **до** его выполнения. Агент намеревается выполнить команду → hook проверяет → разрешает или блокирует с объяснением.

Реализуется в Claude Code через `PreToolUse` hook. В других платформах — через middleware, обёртки над tool-calls, или pre-execution callbacks.

---

## Минимальный набор блокировок

Рекомендуемый минимум для любого production-проекта:

```
Деструктив файловой системы:
  rm -rf /      → BLOCKED [P/Privileged]
  rm -rf .      → BLOCKED [P/Privileged]

Git деструктив:
  git push --force    → BLOCKED [P/Privileged]
  git reset --hard    → BLOCKED [W/Write]
  git clean -fdx      → BLOCKED [W/Write]
  git checkout -- .   → BLOCKED [W/Write]

SQL деструктив без WHERE:
  DELETE FROM <table>  (без WHERE)  → BLOCKED [P/Privileged]
  UPDATE <table>       (без WHERE)  → BLOCKED [P/Privileged]
  DROP DATABASE        → BLOCKED [P/Privileged]
  TRUNCATE             → BLOCKED [P/Privileged]

Защита конфигурации:
  Edit/Write на .env*  → BLOCKED [P/Privileged]
```

---

## Формат сообщения блокировки

Критически важно: hook не просто блокирует — он **объясняет и предлагает альтернативу**.

```
BLOCKED [P/Privileged]: git push --force — принудительная перезапись истории.

Причина блокировки: потеря коммитов, которые видят другие разработчики.

Alternatives:
  1. git push (без --force) — если нет конфликта
  2. git push --force-with-lease — безопаснее, блокирует если кто-то запушил после тебя
  3. Обсудить с командой — может быть нужен другой подход (revert commit вместо force)

Если всё равно нужно — выполни вручную: git push --force origin <branch>
```

Анти-паттерн: блокировка без объяснения и без альтернатив:

```
# Плохо
Command blocked.

# Тоже плохо — альтернатива сама заблокирована
BLOCKED: rm -rf .
Alternative: rm -rf * (тоже заблокирована)
```

---

## Самопротиворечивость

Проверь: предложенные альтернативы в сообщении блокировки не должны сами быть заблокированы тем же hook'ом. Это классическая ловушка: пользователь видит альтернативу, пробует — снова блокировка.

---

## Что hook НЕ делает

- Не блокирует всё подряд (синдром «безопасного» но бесполезного hook'а)
- Не заменяет промпт — он дополняет, закрывая классы ошибок, которые промпт не покрывает надёжно
- Не принимает архитектурные решения — только техническая защита

---

## Принцип минимальной инвазивности

Хороший hook срабатывает редко — только на реальные нарушения. Если hook блокирует рутинные операции, разработчики начнут его отключать. Настраивай паттерны точно.

```
# Плохо — слишком широко, заблокирует обычные операции
rm .*   →  блокировать

# Хорошо — точечно
rm -rf /        →  блокировать
rm -rf .        →  блокировать
rm -rf [путь]   →  не блокировать (это нормальная операция)
```

---

## Когда hook не помогает

Hooks — защита от нечаянных ошибок, не от целенаправленного обхода. Если пользователь сознательно хочет выполнить заблокированную операцию (например, действительно нужен force-push) — он выполняет её вручную. Это правильно: осознанное действие + ручное выполнение = трудно сделать случайно.
