# 07 — Stop Rules: когда агент должен остановиться

## Проблема

Агент без правил остановки будет:
- Делать 4-й, 5-й, 6-й retry «вслепую» после провала первых трёх
- Обходить hook через workaround («так же работает же»)
- Продолжать при 70% заполненном контексте — и терять важное в конце
- Циклиться на деградирующем внешнем сервисе, маскируя проблему
- Включать в коммит чужие незакоммиченные изменения «для удобства»

Шесть правил ниже — минимальный защитный набор.

---

## Правило 1: 3 retry — стоп

После трёх неудачных попыток одной операции — полная остановка.

**Что делать:**
- Сообщить traceback / последнюю ошибку
- Предложить 2-3 альтернативных подхода
- Ждать пользователя

**Что НЕ делать:** 4-й retry «вслепую» с той же стратегией. Если три раза не сработало — проблема не в случайности.

```
# Хорошо
Попытка 1: pip install foo → ошибка зависимостей
Попытка 2: pip install foo --no-deps → ошибка импорта
Попытка 3: pip3 install foo → та же ошибка
→ СТОП. Описываю ошибки, предлагаю: (A) обновить pip, (B) проверить Python-версию, (C) установить вручную

# Плохо
Попытка 4: pip install foo --force-reinstall → ...
Попытка 5: sudo pip install foo → ...
```

---

## Правило 2: hook заблокировал — не обходить

Если защитный hook (`guard.py` или аналог) заблокировал команду — это не ошибка, которую нужно обойти. Это сигнал.

**Что делать:**
- Прочитать сообщение блокировки
- Понять причину
- Использовать безопасную альтернативу из сообщения hook'а (если она есть)
- Если безопасной альтернативы нет — попросить пользователя выполнить вручную

**Что НЕ делать:**
- `--no-verify`
- `$(...)` для скрытой команды
- `git commit -m '...; rm ...'`
- Любая хитрость, которая обходит, а не решает проблему

---

## Правило 3: 70% контекста — чекпоинт

При приближении к лимиту контекста агента (~70% заполнено) — остановиться и зафиксировать состояние.

**Формат чекпоинта:**
```
Контекст заполнен ~70%. Фиксирую прогресс.

Сделано:
- [список]

Осталось:
- [список]

Следующий шаг: [конкретное действие]
```

После чекпоинта — или продолжать в новой сессии, или получить подтверждение продолжать сейчас.

**Почему важно:** при компакции контекста агент теряет детали. Длинные задачи лучше резать на этапы, чем доводить до компакции и получать «агент забыл что делал».

---

## Правило 4: 2 ошибки внешнего сервиса подряд — стоп

Если внешний сервис (LLM-API, S3, любой внешний HTTP API) возвращает ошибки два раза подряд — остановиться.

**Что делать:** сообщить статус пользователю с деталями ошибки.

**Что НЕ делать:** cycличный retry — это маскирует деградацию платформы и может привести к накоплению расходов без результата.

---

## Правило 5: чужие uncommitted — не включать

Перед коммитом проверить `git status`. Если есть несвязанные незакоммиченные изменения от предыдущих операций — **не включать их автоматически**.

**Что делать:**
- Сделать `git add` только своих файлов
- Или спросить пользователя: «вижу изменения в X — включать в этот коммит?»

**Что НЕ делать:** `git add .` или `git add -A` без явного анализа того, что попадёт в коммит.

---

## Правило 6: >15 задач в Todo — переклассифицировать в Tier 3

Если в ходе работы список шагов вырос больше 15 — задача явно крупнее, чем казалась.

**Что делать:**
- Переклассифицировать в Tier 3 (если ещё не)
- Идти через оркестратор с обязательным внешним sanity-check плана
- Сообщить пользователю о переклассификации

**Исключение:** если агент уже работает как оркестратор — не спавнить вложенного оркестратора. Сделать чекпоинт пользователю и спросить продолжать ли.

---

## Общий принцип

Stop rules — это не проявление слабости или неуверенности агента. Это часть архитектуры безопасности. Агент, который умеет остановиться — надёжнее агента, который всегда «до конца».
