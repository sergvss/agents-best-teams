# 01 — Философия: команда агентов

## Манифест

Один агент с большим контекстом и доступом ко всем инструментам — это не серебряная пуля. Это узкое горлышко: он знает всё обо всём, делает всё сам, и именно поэтому регулярно делает что-то не то.

**Команда специализированных агентов** — архитектурный ответ на эту проблему. Каждый агент знает свою зону, работает в явно заданных границах и передаёт эстафету, а не «помогает заодно».

---

## Глоссарий: PRIMARY и SIDE-модели

Методология **не привязана к конкретному провайдеру LLM**. Везде дальше используются роли, а не имена моделей:

| Роль | Что это | Кто подходит |
|---|---|---|
| **PRIMARY** | Главный агент в твоём IDE/CLI. Знает инварианты проекта, имеет persistent memory, видит файлы. | Claude (Claude Code), GPT (Codex / GitHub Copilot Workspace), любая модель в Cursor / Cline / Aider |
| **SIDE-A** | Первый «внешний» ревьюер для триангуляции. Другая компания, чем PRIMARY. | Если PRIMARY = Claude → GPT / Gemini / Grok / Mistral |
| **SIDE-B** | Второй внешний ревьюер. Другая компания, чем PRIMARY **И** SIDE-A. | Третий вендор из списка выше |

**Правило независимости:** PRIMARY ≠ SIDE-A ≠ SIDE-B по **vendor'у** (компания, обучившая модель), не по gateway (через какой API ты их зовёшь). OpenRouter как gateway для обеих SIDE — ок; OpenAI как vendor для обеих SIDE — нет.

**Где это настраивается:** конфиг агентов твоего проекта (пример — `agents.config.example` в корне этого репозитория). PRIMARY определяется тем, в каком CLI/IDE ты живёшь; SIDE-* — это две HTTP-ручки (или один OpenRouter-ключ → две модели разных vendor'ов).

**Связанная роль:** `reasoning-consultant` — разовая консультация SIDE-модели до старта Tier-3 работы (sanity-check плана), не то же самое, что триангулированное ревью после. Технически использует ту же SIDE-A модель из `agents.config`.

## 5 ключевых принципов

### 1. Разделение зон ответственности

Каждый агент описывает не только то, что он делает, но и **явный список того, что он НЕ делает**. Без этого агент будет «помогать» в чужой зоне — и ломать то, чего не знает.

```
# Хорошо — явные границы
## Что НЕ делает
- Не трогает файлы бэкенда (models, routers, schemas)
- Не запускает и не останавливает сервисы — это sysops
- Не коммитит без явного запроса

# Плохо — только позитивное описание роли
## Что делает
- Frontend-разработка, Vue 3, Pinia
```

### 2. Явная маршрутизация через оркестратор

Главный агент — маршрутизатор, не исполнитель. Он получает задачу, классифицирует её по сложности (см. `02-tier-decomposition.md`) и делегирует профильному агенту. Сам исполняет только тривиальные правки (≤30 строк, ≤2 файла).

**Почему важно:** «вызов агента» — это context boundary. Агент-оркестратор тратит контекст на координацию; агент-исполнитель тратит контекст на глубокое понимание своей зоны.

### 3. Триангуляция критичных решений

Одна модель — одна точка зрения. На security-правки, миграции схемы, изменения биллинга — привлекай второй и третий независимый взгляд. **PRIMARY + SIDE-A + SIDE-B** параллельно находят разные классы проблем (см. глоссарий выше). Детали — в `05-triangulated-review.md`.

### 4. Human-in-the-loop для привилегированных операций

Некоторые операции (DDL на проде, рассылка email, удаление пользователей, работа с платёжными данными) не должны выполняться агентом автономно — никогда. Паттерн: агент останавливается, чётко описывает что хочет сделать и почему, ждёт явного подтверждения человека.

Это не слабость системы — это намеренная архитектурная точка контроля.

### 5. Бюджеты вместо «беги пока не упадёшь»

Агент без ограничений будет делегировать бесконечно, пока не исчерпает контекст или не накопит каскадную ошибку. Явные бюджеты делегаций и обязательные чекпоинты дают человеку окно для коррекции курса. Детали — в `04-orchestration-budgets.md`.

## Когда команда агентов нужна

| Признак | Рекомендация |
|---|---|
| 5+ ролей в проекте (backend, frontend, QA, DevOps, docs) | Команда нужна |
| Есть критичные зоны с разными правами доступа | Команда нужна |
| Агент регулярно залезает в чужую зону | Команда нужна |
| Хочется параллельного выполнения независимых задач | Команда нужна |
| Pet-project, один разработчик | Один агент, не нужна |
| Все задачи однородные (только backend) | Специализация не даёт выигрыша |
| Нет времени настраивать маршрутизацию | Начни с одного агента, добавляй по мере роста |

**Практическое правило:** если тебе нужно больше 3 агентов — используй оркестратор. Если 1-3 — можно обойтись прямыми вызовами с явными инструкциями.

---

## Что команда агентов НЕ решает

- Плохо сформулированные задачи. Агент с чёткой ролью не компенсирует размытое ТЗ.
- Отсутствие тестов. Агент-QA пишет тесты, но это не замена продуманной тест-стратегии.
- Архитектурные решения. Агенты — исполнители; архитектуру проектирует человек (или оркестратор после консультации с внешним LLM).
- Безопасность по умолчанию. Hooks и классы риска снижают вероятность катастрофы, но не заменяют security review человека для критичного кода.
