# 05 — Триангулированное ревью

## Идея

Одна модель — одна точка зрения, один набор слепых пятен. Разные LLM-архитектуры находят разные классы проблем: то, что пропустит одна модель, почти наверняка поймает другая.

**Триангуляция:** три независимых ревьюера смотрят на один и тот же diff параллельно, каждый не видит оценок других до завершения своего ревью.

> Терминология PRIMARY / SIDE-A / SIDE-B — см. глоссарий в `01-philosophy.md`. Методология провайдер-нейтральна: PRIMARY — это твоя основная модель в IDE/CLI (Claude / GPT / Gemini / любая), SIDE-* — две внешние модели **от других компаний**.

---

## Состав тройки

| Ревьюер | Роль | Сильная сторона |
|---|---|---|
| **PRIMARY** | Главный агент с контекстом проекта (вызывается так, как принято в твоей платформе — subagent, slash-command, embedded review, прямой вызов из CLI) | Глубокое знание инвариантов проекта, проектных правил, persistent memory, контракта API |
| **SIDE-A** | Вызов через API (HTTP / CLI / SDK) | Другая архитектура — другие слепые пятна |
| **SIDE-B** | Вызов через API | Третий взгляд, часто ловит другие классы ошибок |

**Жёсткое правило:** SIDE-A и SIDE-B должны быть от **разных компаний**, и обе — от компании, отличной от PRIMARY. Минимум три разных вендора → настоящая независимость.

**Типичные сочетания:**

| PRIMARY | SIDE-A | SIDE-B |
|---|---|---|
| Claude (Anthropic) | GPT (OpenAI) | Gemini (Google) |
| GPT (OpenAI) | Claude (Anthropic) | Gemini (Google) |
| Gemini (Google) | Claude (Anthropic) | GPT (OpenAI) |
| любая | любая другая | Grok (xAI) / Mistral / Qwen / Kimi |

Конкретные модели — на твой выбор: главное — три разных **vendor'а** (компании-обучателя модели), не три разных gateway'я. Самый простой способ — один ключ от OpenRouter (gateway), через него доступ к моделям всех vendor'ов сразу. Подробнее про gateway vs vendor — в комментариях `agents.config.example` (в корне репо).

---

## Когда запускать триангуляцию

| Ситуация | Ревьюеры |
|---|---|
| Tier 2 — security / RBAC / API-контракт / миграции | PRIMARY + SIDE-A |
| Tier 3 — крупная фича | PRIMARY + SIDE-A + SIDE-B параллельно |
| Финальная приёмка перед коммитом в прод | Все три одновременно |
| Tier 1 — тривиальная правка | Не нужна |
| Только документация / комментарии | Не нужна |

---

## Правило 2-из-3

Как интерпретировать результаты:

| Ситуация | Действие |
|---|---|
| Все три указывают на одну проблему | Это блокер — фиксить обязательно |
| 2 из 3 указывают на проблему | Серьёзное замечание — разобраться, скорее всего фиксить |
| Только 1 из 3 | Выслушать у PRIMARY, может быть false positive |
| Ревьюеры расходятся | Подсветить пользователю — финальное решение за человеком |

---

## Принцип независимости

Каждый ревьюер завершает свой отчёт **до** того, как видит результаты других. Это критично: если ревьюер знает, что SIDE-A поставил блокер, он подсознательно ищет подтверждение, а не смотрит независимо.

Для SIDE-моделей это автоматически (параллельные вызовы API). Для PRIMARY — он не должен видеть черновики SIDE-ревьюеров до того, как сформирует свой вердикт.

---

## Сильная сторона PRIMARY

SIDE-модели не знают твой проект. Они не знают:
- Какие инварианты нельзя нарушать
- Где в коде архитектурные соглашения, которые нигде не задокументированы
- Что вот эта строка в правилах проекта означает для конкретного эндпоинта

Это сильная сторона PRIMARY — при условии, что он обучен на инвариантах проекта через систему промптов и persistent memory.

Поэтому **PRIMARY никогда не заменяется SIDE-моделью**: он остаётся единственным ревьюером с контекстом. SIDE-модели дают взгляд снаружи, не подменяют его.

## Паттерн вызова SIDE-ревьюера

```bash
# Получить diff
git diff main...HEAD > /tmp/review.diff

# Вызвать SIDE-A через CLI/HTTP-API твоего провайдера
<your-side-a-cli> review --diff /tmp/review.diff --output /tmp/review-side-a.json

# Аналогично — SIDE-B
<your-side-b-cli> review --diff /tmp/review.diff --output /tmp/review-side-b.json
```

Паттерн CLI-обёртки — в `../templates/external-llm-reviewer.md`: структура промпта, JSON-схема ответа и правило агрегации. Готового скрипта в репозитории нет, реализация остаётся на твоей стороне. Конфигурацию (какие модели SIDE-A и SIDE-B, лимиты бюджета) — в `agents.config` проекта, пример в корне: `../agents.config.example`.

---

## Что делать с расхождениями

Если ревьюеры расходятся — не нужно «голосовать большинством» механически. Расхождение само по себе информативно:

- **SIDE-A нашёл SQL-injection, остальные нет** — возможно SIDE-A прав (некоторые модели хорошо ловят security). Проверить вручную.
- **SIDE-B ругает архитектуру, остальные молчат** — возможно стилевое замечание, не блокер.
- **Все трое не согласны друг с другом** — подсветить пользователю, финальное решение не за агентом.

Известные сильные стороны — эмпирические (зависят от поколения моделей), не закладывай их в код жёстко. Раз в квартал переоценивай состав тройки: вышли новые reasoning-флагманы → обнови `agents.config`.

---

## Стоимость и бюджет

Триангуляция стоит денег (каждый прогон SIDE-моделей — это платный API-вызов). Конкретные лимиты — в `04-orchestration-budgets.md` (раздел «Бюджет на платные API»). Минимум:

- Установи лимит `per_review_usd` (например, $0.50) — выше → агент должен спросить у пользователя
- Установи `monthly_usd` — годовой кост-контроль

См. секцию `[budget]` в `agents.config.example`.
