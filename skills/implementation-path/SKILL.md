# Путь от задачи до коммита

Последовательность, в которой каждый шаг заканчивается проверкой, а не ощущением.

1. **Понять** — прочитать существующий код прежде, чем писать новый. Найти, как похожая задача решена рядом.
2. **Спланировать** — короткий план по пунктам, у каждого пункта проверка. Tier 2 и выше на основной ветке — сначала ветка для задачи, скилл `start-branch`.
3. **Реализовать** — минимум кода, решающий задачу. Только то, что напрямую следует из запроса.
4. **Проверить** — тесты, а не «выглядит правильно». Баг и новая логика — скилл `test-first`: тест краснеет до кода. Причина бага неясна — скилл `debug-root-cause` до исправления.
5. **Отревьюить** — свежим взглядом или отдельной ролью. Своя правка всегда кажется понятной. Ведёшь задачу сам, без оркестратора, — шаг всё равно твой: вызови `code-reviewer`, где его требует Tier — на Tier 2 при security, RBAC, API-контракте и миграциях — и тогда плюс одна внешняя модель (SIDE-A), на Tier 3 всегда — и две внешние модели, если они настроены; не настроены — так и напиши в отчёте. Если в проекте включён шлюз ревью, коммит кода без его одобрения откроет человеку окно.
6. **Зафиксировать — только если попросили.** Коммит не входит в «довести до готовности»: запись в историю репозитория делается по просьбе пользователя, а не по факту того, что тесты позеленели. Попросили — сообщение описывает зачем, а не что. Работа шла в ветке — дальше скилл `finish-branch`: влить её решает пользователь.

На каждом шаге действует правило хирургических правок: каждая изменённая строка должна прямо следовать из запроса. Не «улучшай» соседний код заодно.

Полный текст с критериями перехода между шагами и разбором того, где чаще всего срезают углы:

Если методология установлена копированием — файл лежит в `checklists/implementation-path.md` репозитория.
