# Сборка команды агентов под проект

Твоя задача — довести проект от «шаблонов в репозитории методологии» до «рабочих ролей в `.claude/agents/`, адаптированных под этот стек».

Шаблоны лежат в `${CLAUDE_PLUGIN_ROOT}/templates/`. Если методология установлена копированием, а не плагином, — в `templates/` репозитория.

---

## Шаг 1. Пойми проект

Прежде чем что-то предлагать, прочитай проект и определи:

- язык и фреймворк бэкенда, фронтенда;
- ORM и базу данных;
- как запускаются тесты;
- порты dev-серверов;
- есть ли мультиязычность, есть ли E2E-тесты.

Источники: `package.json`, `pyproject.toml`, `go.mod`, `composer.json`, `docker-compose.yml`, `Makefile`, README проекта.

### Если проект новый и читать нечего

В пустом проекте стек не из чего вывести — его нужно **решить и записать**, а не угадать. Спроси у пользователя недостающее и зафиксируй ответы в README, прежде чем идти дальше:

- язык и рантайм бэкенда, фронтенда;
- база данных и способ работы с ней;
- чем запускаются тесты;
- нужны ли локали и E2E;
- порты.

Не подставляй значения по умолчанию молча. Состав команды выводится из стека: решив за пользователя, что тут React и PostgreSQL, ты поставишь роли, которые проекту не нужны, и не поставишь те, что нужны.

**Проверка шага:** ты можешь назвать стек проекта конкретно, а не «веб-приложение», и в проекте есть файл, где этот стек записан.

---

## Шаг 2. Предложи состав команды

Не ставь все двенадцать ролей по умолчанию — это тот самый оверхед, против которого методология и написана.

Минимальный работающий состав: **один dev-агент под основной стек, `qa-tester`, `code-reviewer`**. Остальное добавляется, когда появляется нужда.

Соотнеси роли со стеком:

| Роль | Ставить, если |
|---|---|
| `dev-backend`, `dev-frontend` | есть соответствующая часть проекта |
| `dev-database` | есть миграции и нетривиальная схема |
| `qa-tester` | есть тесты или их надо завести |
| `code-reviewer` | всегда |
| `pm-orchestrator` | ролей больше трёх |
| `browser-tester` | есть UI и настроен Playwright MCP |
| `devops` | есть релизный процесс |
| `docs-writer` | документация поддерживается всерьёз |
| `i18n-keeper` | есть локали |
| `local-sysops` | несколько локальных сервисов и портов |

Покажи предложенный состав пользователю и дождись подтверждения. Состав команды — его решение, не твоё.

**Проверка шага:** пользователь подтвердил список ролей.

---

## Шаг 3. Скопируй и адаптируй

Скопируй выбранные шаблоны в `.claude/agents/` проекта. Затем открой каждый и адаптируй.

**Заменять нужно установочные плейсхолдеры:**

| Плейсхолдер | Чем заменить |
|---|---|
| `<your-project>` | название проекта |
| `<backend-framework>`, `<frontend-framework>` | реальные фреймворки |
| `<порт>`, `<ваш-бэк-порт>`, `<ваш-фронт-порт>` | реальные порты |
| `<ваш>`, `<ваша>`, `<ваши>` | выбор из списка рядом |
| `<reasoning-LLM>`, `<мощный reasoning-LLM>`, `<мощный LLM>`, `<быстрый LLM>` | значение поля `model` |
| `<your-agent-dir>` | каталог агентов платформы |

В строках вида `Python 3.10+ / Node.js / Go / <ваш>` нужно **оставить один вариант** и удалить остальные вместе с плейсхолдером, а не дописывать значение рядом.

**Не трогать то, что заполняется по ходу работы.** В шаблонах есть разметка отчётов и рецептов — `<что сделать>`, `<step>`, `<вердикт>`, `<описание>`, `<PORT>` в командах вида `lsof -ti :<PORT>`. Это не плейсхолдеры установки, а места, которые агент заполняет во время задачи. Замена их сломает шаблон.

Различай по правилу: если значение одинаково для всех задач проекта — заменяй; если меняется от задачи к задаче — оставь.

**Проверка шага:**

```bash
grep -rEn '<your-[a-z-]+>|<ваш[а-и]?>|<ваш-[а-яa-z-]+>|<backend-framework>|<frontend-framework>|<порт>|<reasoning-LLM[^>]*>|<быстрый[^>]*>|<мощный[^>]*>' .claude/agents/
```

Должно вернуть пусто.

## Шаг 4. Сведи роли друг с другом

Шаблоны написаны как самостоятельные, но команда работает только если роли согласованы:

1. В `pm-orchestrator` приведи таблицу маршрутизации к тем ролям, которые реально поставлены. Ссылки на отсутствующие роли — источник тупиков, а отсутствие поставленной роли означает, что её не позовут никогда.
2. Заполни в этой таблице колонку «владеет файлами» реальными путями проекта. Это и есть граница зон: пока у части проекта нет ровно одного хозяина, роли будут наступать друг на друга, сколько бы ни было написано в их промптах.
3. Проверь, что зоны не пересекаются и не оставляют дыр: каждый каталог с кодом упомянут ровно один раз.
4. Сверь набор инструментов каждой роли с матрицей разрешений — скилл `permission-checklist`.

**Проверка шага:** в маршрутизации оркестратора нет ролей, которых нет в `.claude/agents/`, и наоборот — каждая поставленная роль в ней присутствует.

---

## Шаг 5. Расскажи, что осталось

Сообщи пользователю, что сделано, и назови оставшиеся шаги, не выполняя их без спроса:

- **Защитные хуки.** Если методология поставлена плагином — уже работают. Если копированием — нужно скопировать `hooks/guard.py` и подключить конфигурацию.
- **`agents.config`** — нужен только для триангулированного ревью внешними моделями. Для Tier 1 и Tier 2 не требуется.
- **Персональная память ролей** появится сама при первой работе агентов.

Финальный отчёт — короткий: какие роли поставлены, что адаптировано, что осталось за пользователем.
