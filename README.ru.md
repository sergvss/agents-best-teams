Методология и плагин Claude Code для разработки программ **командой AI-агентов**. Три слоя в одном плагине: **процесс разработки** от просьбы до слитой ветки — уточнить задачу, спланировать, увести в ветку, тест сначала, отладка от корня, ревью; **защитные хуки**, которые останавливают разрушение механически, а не просьбой; и **команда ролей** с явными зонами и маршрутизацией. Для тех, кто использует Claude Code, Codex, Cursor или любой другой agent-CLI и хочет перейти от «одного суперагента на всё» к команде, которая работает по процессу.

---

## Зачем

| Ситуация | Что берёшь |
|---|---|
| Стартуешь проект и сразу хочешь команду ролей, а не одного агента | скилл `setup-agent-team` соберёт состав под твой стек |
| Агентов уже десяток, каждый лезет в чужую зону | `principles/02` и шаблон оркестратора — маршрутизация по Tier |
| Агент что-то снёс, и это не должно повториться | `hooks/` — рабочие защитные хуки, ставятся вместе с плагином |
| Критичные правки уходят в прод «на глаз» | `principles/05` — три модели от разных вендоров, правило 2-из-3 |
| Нужен аудит того, что уже настроено | `checklists/` — матрицы разрешений, контекста, планирования |
| Хочешь, чтобы агент работал по процессу, а не импровизировал | процессные скиллы — `clarify-task`, `start-branch`, `test-first`, `debug-root-cause`, `finish-branch` |

## Процесс разработки

Плагин закрывает весь путь от просьбы до слитой ветки. Каждый шаг — скилл, который открывается до первой правки кода. Одна строка в контексте сессии называет их: на простых задачах модель пропускает скиллы, о которых ей не напомнили.

```
просьба ──► clarify-task: сначала изучить проект, потом одно сообщение —
            что понял, 2-3 подхода с рекомендацией,
            не больше трёх вопросов, меняющих результат
        ──► Tier
   Tier 1 ─► правка на текущей ветке
   Tier 2 ─► start-branch ─► test-first ─► ревью, если рискованно ─► finish-branch
   Tier 3 ─► план: файлы, интерфейсы, Run/Expected, Review Focus
           ─► свежий читатель проверяет план ─► ты его утверждаешь
           ─► start-branch ─► задачи по одной, рискованные — с ревью сразу
           ─► финальное ревью ветки ─► finish-branch
баг ─────► debug-root-cause ─► test-first
```

- **Ветки.** Задача Tier 2 и выше уходит с основной ветки; политика проекта — в `git config abt.branches`. В конце — меню: слить, pull request или оставить, выбираешь ты. Удалить неслитую работу можно только твоим словом: на `git branch -D` хук спросит.
- **Тест сначала.** Красный тест до кода, и падать он должен по нужной причине. Код, написанный до теста, не удаляется: тест обязан покраснеть, когда поведение сломано нарочно.
- **Исполнение плана Tier 3.** Каждая роль получает свою задачу, а не весь план. После утверждения плана оркестратор решает мелочи сам и записывает каждое решение; останавливается только на необратимом, безопасности, действии за пределами ветки и сломанном плане.

Замерено, а не предполагается: красный тест до кода — 0 из 2 прогонов без скиллов, 3 из 3 с ними; расплывчатая просьба в один раунд — 0 из 3 до, 2 из 3 после; задача Tier 3 прошла от плана до слитой ветки и пережила по дороге обрыв сессии. Откуда идеи и чем мы отличаемся — [docs/superpowers-comparison.md](docs/superpowers-comparison.md).

## Установка

### Быстрый старт

Шесть шагов от нуля до работающей команды. Каждый разобран ниже — если что-то пошло не так, ответ там.

| | Что сделать |
|---|---|
| 1 | `/plugin marketplace add sergvss/agents-best-teams` |
| 2 | `/plugin install agents-best-teams@sergvss` |
| 3 | `/reload-plugins` — **только если** Claude Code написал `Run /reload-plugins to activate.` До этого не работает ничего |
| 4 | Хуки говорят по-английски. Нужен русский: `mkdir -p .claude && printf 'ru\n' > .claude/.abt-lang` |
| 5 | Вставить в чат: `Разверни команду агентов в этом проекте через скилл agents-best-teams:setup-agent-team` |
| 6 | Проверить: попросить агента выполнить `echo проверка > .env.check`. Должно заблокироваться |

Шаги 1-3 занимают минуту, шаг 5 — несколько минут и пару решений от тебя. Шестой не пропускай: незапустившийся хук неотличим от отсутствующего, и узнать об этом лучше сейчас, чем в тот день, когда он был нужен.

На macOS и Linux шестой шаг, скорее всего, покажет проблему — см. ниже.

> **Не опечатка, что `sergvss` в двух строках значит разное.** В первой это **адрес репозитория** на GitHub, во второй — **имя маркетплейса**, заданное внутри него.
>
> Если добавляешь маркетплейс через окно **Manage Plugins → Marketplaces → Add**, в поле нужен именно адрес: `sergvss/agents-best-teams`. Одно слово `sergvss` там даст ошибку `Invalid marketplace source format`.

### Что включается когда

Не всё начинает работать в момент установки — вот точная картина.

| | Когда | Что это |
|---|---|---|
| **Защитные хуки** | сразу | Блокируют деструктив ФС, запись в `.env` и SQL без `WHERE` в клиентах БД (`psql`, `mysql`, `sqlite3` и других); перед force-push, `reset --hard` и `DROP` спрашивают вас в окне подтверждения Claude Code, как и перед коммитом кода без одобрения `code-reviewer` (если в команде есть `code-reviewer` и шлюз включён пустым файлом `.claude/.review-gate`); ведут журнал привилегированных действий и останавливают слепые повторы падающей команды |
| **Правило после отказа** | со следующего старта | Если auto mode отклонил действие, агент спрашивает вас через меню вопросов, а не пишет «выполните сами». Роль передаёт просьбу главному диалогу: субагенты спрашивать не могут |
| **Процесс разработки** | сразу; строка в контексте — со следующего старта | Скиллы `clarify-task`, `start-branch`, `test-first`, `debug-root-cause`, `finish-branch`; одна строка в контексте сессии называет их со следующего старта сессии; хук говорит агенту, что он правит основную ветку |
| **Чек-листы как скиллы** | сразу | Claude подтягивает их сам, когда они уместны, или вызывай через `/` |
| **Разбор решений хуков** | сразу | Спросите, откуда окно или блокировка: скилл `diagnose-hooks` читает транскрипт сессии, цитирует `файл:строка` для каждого решения хука и говорит, повторится ли оно в текущей версии |
| **Предложение собрать команду** | со следующего старта | Это хук на `SessionStart`: событие уже прошло, если ставил посреди работы. Подойдёт и `/clear` — переигрывать сессию целиком не нужно, но `/reload-plugins` не поможет |
| **Роли команды** | только вручную | `setup-agent-team`, см. ниже |
| **Stop-хук `verify.py`** | одна строка настроек | Плагин его подключает, но хук молчит, пока не задана команда тестов в файле пользователя `~/.claude/agents-best-teams/verify.json`: `{"C:/projects/my-app": "npm test"}`. Вне репозитория намеренно: чужой репозиторий не подложит команду. Подробно — [hooks/README.md](hooks/README.md) |
| **Триангуляция** | только вручную | Нужен `agents.config` и ключи внешних моделей — [docs/models.md](docs/models.md) |

**Сначала активация.** После установки Claude Code пишет либо `Plugin is now active.`, либо `Run /reload-plugins to activate.` Во втором случае до выполнения этой команды не работает ничего.

**На macOS и Linux хуки скорее всего промолчат.** В конфигурации указан `python`, а там бинарник называется `python3` — хук не запустится, и это не видно без проверки. Менять нужно **все вхождения**, а не первое: их девятнадцать на файл конфигурации, и если поправить один блок, журнал, счётчик повторов, шлюз ревью и подсказка при старте останутся молчать. Готовая команда — в [hooks/README.md](hooks/README.md#требования).

### Команду ролей нужно развернуть отдельно

Хуки и скиллы работают сразу, а вот **роли плагин намеренно не ставит**: в шаблонах плейсхолдеры под конкретный проект, и роли с `<your-project>` внутри были бы хуже, чем их отсутствие. К тому же файлы плагина перезаписываются при обновлении — твои правки в ролях пропадали бы.

При первом запуске в проекте без команды Claude сам предложит её собрать. Если ждать не хочется — скопируй эту строку в чат:

```
Разверни команду агентов в этом проекте через скилл agents-best-teams:setup-agent-team
```

Скилл прочитает стек, предложит состав ролей, скопирует шаблоны и адаптирует их под проект. Отключить предложение навсегда: создать пустой файл `.claude/.no-team-setup-prompt`.

> **Проверь, что хуки работают:** попроси агента выполнить `echo проверка > .env.check`. Команда должна быть заблокирована с объяснением. Если вместо этого появился файл — хуки не подключились, смотри [hooks/README.md](hooks/README.md#проверь-что-защита-встала--это-обязательный-шаг).
>
> Проверять защиту опасной командой вроде `rm -rf .` нельзя: если хук не работает — а именно это ты и проверяешь, — она выполнится.

Роли из `templates/` работают со всеми, но часть полей у тиммейтов не применяется — разбор в [docs/claude-code-mechanisms.md](docs/claude-code-mechanisms.md).

## Обновление

```
/plugin marketplace update sergvss
/reload-plugins
```

Две вещи, из-за которых обновление «не приходит», хотя всё сделано правильно:

- **Сторонние маркетплейсы не обновляются сами.** Автообновление по умолчанию включено только у официальных маркетплейсов Anthropic. Включить: `/plugin` → вкладка **Marketplaces** → `sergvss` → **Enable auto-update**.
- **Новая версия видна только после подъёма `version` в манифесте.** Если автор залил изменения, не подняв версию, до установленных плагинов они не доедут.

### При ручном обновлении не перезаписывать

| Никогда | Почему |
|---|---|
| `.claude/agent-memory/` | Накопленное знание ролей, восстановлению не подлежит |
| `.claude/approval-log.jsonl` | Журнал привилегированных действий |
| `.claude/settings.json` | Твои настройки — новые блоки хуков переносить руками |
| `.claude/.abt-lang` | Выбранный язык сообщений хуков |
| `.claude/agents/` | Роли адаптированы под твой проект |

Обновлять можно `hooks/*.py` и `skills/`. Настройки под проект — свои роли, клиенты БД, раскладка тестов — живут в `.claude/agents-best-teams.json`, и обновление их не трогает. Если в старой версии правил константы прямо в `guard.py`, перенеси их в этот файл: [hooks/README.md](hooks/README.md#файл-настроек-проекта).

С последней строкой таблицы неудобно, и это честно: слить изменения шаблона с уже адаптированной ролью может только человек. Совет — закоммитить `.claude/` сразу после установки: тогда видно, что правил ты, а что осталось шаблонным.

**Подробно, включая путь для тех, кто ставил до 1.0.0** — [docs/update.md](docs/update.md).

## Что внутри

Методология фокусируется на **командной работе** агентов, а не на одиночных:

- **Tier-декомпозиция задач** — pipeline зависит от размера задачи, а не наоборот
- **Изоляция зон ответственности** — каждый агент знает свою зону и не лезет в чужую
- **Триангулированное ревью** — критичные решения проверяют 3 модели от разных вендоров, правило 2-из-3 = блокер
- **Persistent memory per-agent** — институциональное знание накапливается между сессиями
- **Human-in-the-loop** для привилегированных операций
- **Eval-suite** для агентного слоя — те же тесты, что для продуктового кода
- **Механические инварианты** — повторяющаяся ошибка становится кодом, а не новой строкой в промпте
- **Недоверенный ввод** — текст из тикетов, страниц и ответов API это данные, а не инструкции

Механические инварианты здесь не обещание, а работающий код: `hooks/` покрыты тестами, и половина из них проверяет **отсутствие** ложных срабатываний. Хук, который мешает работать, отключают в первый же день — и защиты не остаётся вовсе.

Каждый принцип разобран на примере «плохо → хорошо» в [EXAMPLES.md](EXAMPLES.md).

## Когда команда нужна

**Нужна**, если:
- В проекте 5+ ролей: backend, frontend, QA, DevOps, документация
- Есть критичные зоны с разными правами (прод, биллинг, RBAC)
- Агент регулярно «залезает» в чужую зону и ломает что-то
- Хочется параллельного выполнения независимых задач

**Не нужна**, если:
- Pet-project на одного разработчика
- Задачи однородные (только backend или только frontend)
- Нет времени настраивать — один опытный агент быстрее

## Структура

```
principles/    11 принципов: философия, Tier-декомпозиция, классы риска,
               бюджеты и кэширование, триангуляция, память, stop rules,
               approval log, механические инварианты, eval-suite,
               недоверенный ввод

               делают: backend, frontend, database, QA, DevOps,
                       документация, мультиязычность, локальный sysops
               смотрят: ревьюер кода, безопасность, интерфейс,
                       расследователь, вызов скоупу
               считают: стоимость эксплуатации, юнит-экономика,
                       инвестиционная отчётность, подписки и лицензии

                       внешний LLM-ревьюер

               планирование, путь от задачи до коммита, ветки,
               тест сначала, отладка от корня,
               уточнение задачи без интервью

hooks/         Рабочие защитные хуки — слой Claude Code
               guard.py — блокировка деструктива до выполнения
               verify.py — не завершать работу с падающими тестами
               approval_log.py — журнал привилегированных действий
               ledger_log.py — вызовы ролей в ledger задачи
               branch_hint.py — подсказка «ты правишь основную ветку»
               retry_guard.py — правило трёх попыток
               review_gate.py — шлюз ревью для коммитов кода (включается)
               session_start.py — подсказки при старте сессии
               denial_guidance.py — что делать после отказа
               messages.py — все сообщения, на двух языках
               конфигурации и тесты

skills/        Процесс разработки, чек-листы как вызываемые скиллы,
               сборка команды под проект

docs/          Установка, обновление, настройка моделей, первый запуск,
               выбор механизма запуска, проверка работоспособности,
               concepts.en.md — термины методологии по-английски

.claude-plugin/  Манифесты плагина и маркетплейса

EXAMPLES.md    Каждый принцип в виде «плохо → хорошо»
CHANGELOG.md   История изменений
VERSION        Текущая версия, сверяется с манифестом в CI
```

> К Claude Code привязаны только `hooks/`, `skills/` и `.claude-plugin/`. Всё остальное провайдер-нейтрально; эквиваленты для других платформ описаны в [hooks/README.md](hooks/README.md#другие-платформы).

## Принципы одной строкой

1. **Команда агентов > суперагент** — специализация снижает ошибки зон ответственности
2. **Tier-декомпозиция** — размер задачи определяет pipeline, не наоборот
3. **R/D/W/P классы риска** — подтверждение только там, где оно нужно
4. **Бюджеты и кэширование** — чекпоинт после N шагов; стабильное в начало промпта, изменчивое в конец
5. **Триангуляция** — критичные решения проверяют 3 модели параллельно
6. **Persistent memory** — институциональное знание агента между сессиями
7. **Stop rules** — агент знает когда остановиться, не застревает в петлях
8. **Approval log** — привилегированные действия оставляют след
9. **Mechanical invariants** — повторяющиеся ошибки → hooks, не уговоры
10. **Eval-suite** — агентный слой тестируется так же, как продуктовый код
11. **Недоверенный ввод** — внешний текст это данные, а не инструкции

## Два языка

Вы читаете русскую версию — [README.ru.md](README.ru.md). По умолчанию GitHub показывает английскую, [README.md](README.md); переключатель бейджами в шапке обоих файлов.

**Почему английский стал основным.** GitHub не умеет выбирать язык по локали посетителя — никакой автоматики тут нет вообще, и это [давняя просьба к платформе](https://github.com/orgs/community/discussions/179316), а не наш недосмотр. Единственный рабочий способ — второй файл и явная ссылка между ними, по сложившейся конвенции `README.<код языка>.md`. Основным при этом принято держать английский: репозиторий публичный, и первым его открывает кто угодно.

Отсюда правило сопровождения: **отставать разрешено только русской версии**. То, что посетитель видит первым, обязано быть верным; расхождение по фактам не допускается ни в какую сторону. Версия в бейджах у обоих общая, потому что читается из одного манифеста.

**Переводится не всё, и это осознанно.** У содержимого пять слоёв, и цена перевода у них разная:

| Слой | Язык | Почему так |
|---|---|---|
| README | EN + RU | Витрина: по ней решают, брать или нет. Дублировать дёшево |
| Сообщения хуков | EN + RU | Единственное место, где язык мешает работать: блокировку читают, когда уже что-то пошло не так |
| Метаданные плагина и описания скиллов | EN | 10 строк. Их видно в `/plugin`, `/help` и в каталоге |
| Страница концепций для англоязычных | EN | Не перевод прозы, а термины: Tier, классы риска, 2-из-3, память ролей |
| Принципы, шаблоны, чек-листы, `docs/` | RU | Несколько тысяч строк прозы, меняется каждый выпуск |

### Как выбрать язык хуков

По умолчанию хуки говорят **по-английски**: плагин публичный, а непонятный язык блокировки хуже понятного. Русский возвращается одной строкой:

```bash
ABT_LANG=ru claude                                    # на одну сессию
mkdir -p .claude && printf 'ru\n' > .claude/.abt-lang # постоянно для проекта
```

Правила от языка не зависят — блокируется одно и то же. Незнакомое значение откатывается на английский и защиту не снимает.

Если язык не выбран, плагин спрашивает его в начале каждой сессии, пока вы не выберете. Скилл `setup-agent-team` спрашивает его при развёртывании команды, записывает ответ в `.claude/.abt-lang` и заодно может выдать сами роли на нужном языке — в репозитории при этом остаётся одна каноническая копия, расходиться нечему.

**А работать-то оно на английском будет?** Механически да, и это не догадка про модель, а свойство слоёв. Роли и скиллы — это промпты: модель читает русское определение роли и отвечает на языке собеседника. Хуки — обычный Python, им язык безразличен.

**Где упрётся.** Не в хуках: их сообщения существуют на обоих языках, и `ABT_LANG=ru` возвращает русский целиком. Упрётся в прозе — принципах, шаблонах ролей, чек-листах. Английский читатель получит понятную блокировку и русский документ, на который она ссылается.

**Почему не перевести всё.** Вторая копия начнёт расходиться с первой, а шаблон роли, который тихо противоречит русскому оригиналу, опаснее отсутствующего: по нему работают, не имея возможности сверить. Переводу нужен сопровождающий, а не разовый проход. Единственное место, где язык действительно мешал работать, уже закрыто каталогом сообщений — дальше начинается проза, у которой другая цена.
